claude-issue-agent · 常驻会话 · /loop 编排

Issue → PR 流水线

一个常驻的 Claude 会话用 /loop 周期轮询,会话始终存活、持续复用同一上下文。GitHub label 就是状态机:每个 tick 拉取 issue,把只读的 triage 与 worktree 里的开发派发给受限 sub-agent。唯一的人工闸门,就是给 issue 打上 claude:approved。点击推进,或点任意阶段查看细节。

执行机制 · 一个常驻会话,三层协作

1

驱动层 —— /loop 周期轮询

一个常驻的 Claude 会话,用 /loop 每隔几分钟触发一次;会话始终活着,持续复用同一上下文。每个 tick 只做一轮「拉取 issue → 按 label 分发」。这一层不是 skill 也不是 sub-agent,就是会话本身。

内置 /loop
2

编排层 —— 状态机 skill

唯一真相源是 GitHub label。skill 定义「什么 label → 走哪个阶段 → 加/删哪个 label」,并按父子依赖把队列排成串行计划。会话崩了重启,靠 label 自动续跑 —— 天然幂等。

issue-agent skill
3

执行层 —— 受限 sub-agent

triage 与 develop 这类重活各自跑在独立 sub-agent 里:按阶段限定工具白名单(triager 只读、developer 可写 + worktree),隔离上下文,不撑爆常驻主循环。

issue-triager / issue-developer

串行调度 · 一次只推进一棵父树

Issue 之间可以有父子关系(epic → 子任务 —— 例如 epic #17 就列了 9 个)。编排层按依赖排序,一次把一棵父树推到底:先所有子任务、再父任务,直到整棵树都停在人工闸门上(claude:approved 或 PR review)。只有这时才开始下一棵树 —— 两个 epic 绝不交错进行。
