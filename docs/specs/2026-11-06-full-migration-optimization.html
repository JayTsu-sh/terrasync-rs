01 / SCOPE范围与设计原则

本方案覆盖保留源端的复制，以及目标就绪后删除源端的搬迁。全量不支持断点续扫。保留源端任务失败后重新扫描并增量比较；当前删除源端时，上一代保留源端则做增量，上一代删除源端则重新全量，不复用其基线。这条代次规则同时覆盖上一代成功、失败和取消。

推荐优先完善现有 unordered 扫描、路径分派和目录统一收尾机制。只有需要提前完成子树时，再引入目录完成屏障；不将切换 blocks 或合并全部历史版本作为正确性的替代方案。

完成条件：保留源端时，目标文件和目录达到约定状态；删除源端时，还要确认迁移范围内的源项清理完成。结果未知、清理失败和通知失败分别表达。

删除硬约束：任何数据或所需元数据复制、应用、校验错误尚未解决，目标发布或持久性未确认，都不得删除对应源对象。目标就绪并复核源身份后可以删除，ClickHouse 记录异步批量写入；允许少量记录缺失，不为此增加逐文件确认或专门对账流程。版本化源必须先完成该 key 按目标策略要求的全部迁移结果，再永久清理全部源历史。

版本化源的确定规则：非多版本目标只复制最新可见版本，多版本目标按源历史顺序复制；启用删除源端时，两种目标都永久删除已迁移 key 的全部源历史记录，包括数据版本与 delete marker。非多版本目标不保存旧历史是本迁移策略的既定语义，不能据此拒绝全部历史清理，也不能声称目标保留了完整历史。

版本入库与计数：非版本化目标在 ClickHouse 中只保存最新版本／最新状态，不落旧历史版本明细；版本化目标保存所复制的历史版本。无论一个 entry 含多少版本，统计只计一次，不能以版本数或入库行数替代 entry 数。

错误上报口径：所有最终未恢复的错误都必须在 callback 中明确体现，不限于复制错误。配置预算内重试后恢复成功的错误仅记录日志，不进入 callback 错误明细或错误计数；恢复过程中不能提前授权删除，恢复后仍需重新确认全部前置条件。

校验策略：默认快速校验，仅校验计划要求的元数据；命令行显式要求全量校验时，同时校验文件数据与元数据。保留源端、删除源端两种模式遵循同一选择，删除前必须通过所选校验并确认目标就绪，不等待单项入库。快速校验通过不等于内容已校验。

源端元数据获取失败：在仍可定位和读取源对象数据时，元数据未获取成功不阻断数据复制。数据结果与元数据错误分别记录，明确提示“源端元数据获取失败”；最终未恢复时进入 callback，重试恢复成功仅记日志。不能把数据复制成功当成完整迁移成功，也不能因数据已入库就删除元数据仍失败的源对象。

扫描前确定元数据 plan：提前列明获取／跳过类别、额外请求成本和预算。源元数据在扫描阶段获取，原值与分类摘要共同保存到 ClickHouse；增量比较查询按需一次带出原值供后续复制复用，不因原值较大改为仅存摘要、二次查库或复制时回源重取。普通 NFS→S3 无用途 ACL／xattr 明确跳过，不发额外请求。

网络中断处理：单次超时／连接异常先作为疑似故障，在短而有界的确认窗口内复核，防止网络抖动误触发退出。疑似期间暂停相关新增工作与源删除；稳定恢复后按副作用证据安全继续，仍未知对象保持删除阻断，该次抖动仅记日志。持续失败确认中断后优雅退出并 callback，窗口不被并发或反复抖动重置。

失败后再次执行：上一代保留源端时，下一次可增量比较已经入库的复制事实，缺失记录允许重新复制；当前删除源端且上一代也删除源端时，必须重新全量并清空旧 base。不会为了恢复删除代次的少量入库缺失而新增目标端对账、持久化回执或本地扫描暂存。

文件传输模式：支持文件级断点续传，对应 data-mover 的 Checkpointed；不启用续传时固定使用 Direct，不再增加 Atomic 选择参数。文件续传状态不决定全量／增量扫描选择，也不表示支持断点续扫。

目标数据清理：数据复制最终失败时，删除本次失败复制产生的对应目标数据及失效续传状态；仅元数据获取、应用或校验失败时，保留已复制目标数据。两种情况都不得删除源端，清理失败或结果未知必须准确记录并在 callback 上报。

非空尾斜杠对象：对象 key 以 / 结尾且内容非空时，目标为非对象存储则自动忽略该对象并保留源端；目标为对象存储则保留原始 key，正常复制内容与所需元数据／版本历史。只忽略该实际对象，不剪枝同前缀下的其他对象。

本次全量迁移的性能目标：与优化前相比，整轮性能和内存开销均应相当。元数据观察、摘要、校验、异步批量入库、源清理和目录收尾全部计入。不以小概率入库缺失为由引入常态逐对象等待或额外持久化链路。

当前处于首次开发阶段，可直接调整任务契约、状态格式、表结构及 callback，无需设计旧版本兼容层。当前数据正确性、幂等、恢复和性能约束仍然有效。

03 / COPY保留源端的全量迁移

对应问题：目录 mtime、base 清理、统计、多版本顺序、扫描 plan、网络故障和偶发复制失败。

3.1　目录 mtime：保留统一收尾，补齐完成屏障

目录 mtime 应在目标目录中最后一次创建、删除、rename 等目录项操作之后设置。扫描结束或 blocks 的目录块结束，只能证明枚举阶段推进，不能证明异步复制和发布已经结束。

  1. 扫描时捕获源目录原始元数据，包括迁移根目录和空目录。
  2. 先创建目标目录，并保留后续写入、遍历和收尾所需权限。
  3. 并发迁移内容，等待所有目标命名空间操作、重试和未知结果对账结束。
  4. 应用目录最终元数据并回读确认；全部必需操作成功后，才确认任务完成。

只恢复 mtime 时，全局命名空间操作结束后可以并发执行。最终 mode、ACL 可能收紧父目录权限，应采用从深到浅的顺序，避免阻断后代收尾。

补齐无数据库模式的目录跟踪与收尾。跟踪队列和在途任务有界，不为全部扫描项常驻明细，不新增本地扫描暂存。ClickHouse 仍承担配置启用时的事实及最终报告保存，但单项入库确认不再授权源删除。

blocks 的适用点：未来需要提前完成某个子树时，可结合 blocks 的枚举边界，增加“枚举完整 + 相关 worker 全部确认 + 无待重试或未知操作”的目录完成屏障。blocks 本身不是该屏障。

代次选择使用开始时持久化的源保留策略，不能只看最后成功代次，否则失败或取消的删除任务会被误判。模式判定、执行独占、旧执行收束、任务绑定及 base 准备在任务层／db 统一处理。查询失败明确上报，不根据 job_dir 存在与否猜测模式。

删源迁移的 base 生命周期：本轮复制、目录元数据收尾及源清理仍需使用 base，不能中途全表清空；这些操作结束且所有写入者已收束后，清空该 job 的全部 base 内容，不留下后续增量基线。正常失败收尾也尝试清理；强制退出或清理未确认时，在下一轮取得独占并收束旧执行后强制清理。只清理 base，不删除独立的代次源保留策略、最终报告或错误归档；不把这次整轮清理放进逐文件删源的等待链路。

当前实现已保证上一删除代次之后无论本代是否保留源端，都重新全量并在启动前同步清空 base；Single／双副本 Cluster 和真实 Local 复制／受保护删源后的策略切换验证通过。本轮结束即清理 base 的流程仍待接入，不能将“下一轮启动清理”的测试当作“本轮结束 base 已为空”的证据。收尾清理须保持执行隔离，避免旧执行的延迟清理影响新轮次。

新全量顺序：取得独占 → 确认旧执行停止 → 清理本 job 的 base 与本轮临时状态 → 确认清理 → 启动扫描。Single／Cluster 的物理表及副本差异归 db；不能将发出异步 DELETE 当作清空确认，也不能清理其他 job。

异步入库缺失是允许的低概率代价：保留源端时，增量可能重新复制；删除源端后，下一删除代次重新全量，不要求补记已搬走对象。不会为了记账完整性新增目标对账、持久回执或本地暂存。源缺失不得触发删除任务对目标的反向删除。

版本化目标的同次运行重试仍需核实发布归属，防止响应丢失时盲目重放；代次规则不消除存储协议的幂等要求。每轮身份隔离和旧执行收束仍有效，不能让晚到写入污染新代次。

3.2.1　统一计划：迁移模式与目标清理分别决策

已确定的时间窗口策略：Incremental + Preserve。上一代保留源端、任务绑定及复制契约可复用时，时间窗口变化仍按增量处理：重新枚举并按当前过滤条件比较，复用已确认目标事实，只复制本轮命中的新增／变化项。对本轮未观察项保留目标及确认事实，不因窗口变化强制全量，不逐项回源确认后改为目标删除。上一代删源、本轮无可复用确认事实等全量条件仍优先适用；相同 job ID 的源／目标绑定变化则报错退出。

计划由 app 的迁移模块统一生成，CLI 和 Web 只提交结构化请求并展示结果；db 负责状态、确认事实和 Single／Cluster 的准备与清理，data-mover 负责过滤语义、能力和存储操作。job ID 用于定位对应数据库／作业命名空间内的历史，不能单独证明源根、目标根及复制契约相同。原始命令行用于脱敏审计，不能靠解析其字符串或读取 job_dir 来决定模式。

当前源保留设置来自配置，同一条 sync 命令也可能产生不同策略。入口应将配置优先级解析后的有效策略固定到本轮请求，计划及 worker 使用同一不可变值，避免并发任务重复读取可变化的全局配置而产生分歧。

目标保留计划下，可以省去纯粹为了删除而枚举所有旧 base 缺失项的阶段。比较阶段仍须处理新路径：若稳定句柄相同但当前源路径尚无目标确认，不能把它当成无变化后又跳过 rename 阶段；应复制到新路径并保留旧目标，或在取得真实旧源缺失证据后执行受保护 rename。只在最终 delete 分支加 continue 不足以完成本方案。

3.2.2　本轮未观察项：何时必须回源确认

源缺失判定的统一保守规则：凡是不能可靠确定源项已删除的场景，一律保留目标，不执行基于缺失的目标删除或破坏性 rename。包括过滤出界、目录剪枝、扫描不完整、元数据缺失、基线缺失、源端访问失败、返回语义不明确及证据已失效等情况。只有明确的源缺失证据、本轮目标清理许可、目标归属核验和有效执行身份同时满足，才允许相应清理；时间窗口及删源迁移的 Preserve 计划即使取得源缺失证据也继续保留目标。

不能将保守保留记成删除成功，不能因未确认的源删除而撤销目标确认事实。网络、权限等最终未恢复错误仍须准确进入 callback；重试恢复的错误仅写日志。此规则针对由源缺失推导的目标清理；本次失败复制产物的清理，以及显式的基线失效／整轮清空，仍遵循各自既定契约，不能冒充源项删除。

所有最终保守保留决定必须在 callback 中体现：不能只记日志或静默 continue。对已识别的 entry 交付保留事件，说明源／目标路径、源存在性实际状态和保留原因；未取得存在性证据时明确 Unknown，不能伪报源存在、已过滤或删除成功。共享事件代码为 target_preserved，结构化 retention 字段进入 CLI／Web 共用任务契约；retention.scope 为 entry 时表示整个逻辑路径／key，包括该路径已保留的目标版本。

对没有逐项展开的窗口外集合，callback 明确报告适用范围、Preserve 策略及未逐项核验，不能虚构逐路径原因或已知数量；对已经识别的 entry 则完整交付明细。扫描中断时报告受影响范围和实际故障，不为所有尚未访问项伪造错误，也不为补报路径而逐项回源增加 stat／HEAD。

“本轮未观察到”既不等于“被过滤”，也不等于“源端不存在”。它还可能来自目录剪枝、未完成枚举、访问失败或源端变化。只有已经取得本项观察且实际过滤不匹配，才可明确标记为本轮不在范围。默认 Preserve 时不需要为全部未观察项逐个 stat／HEAD；只有准备执行目标删除、依赖旧路径消失的 rename，或必须报告“已证实源删除”时，才按需确认。显式使基线失效／整轮清空不需要为每个旧项回源，不能把这种记账清理说成源项已删除。

时间窗口变化固定采用增量＋保留目标：不为全部窗口外旧项增加 stat／HEAD，真实源删除也不自动传播到目标；重新命中时比较保留的确认事实，避免无变化数据重复复制。即使其他操作已经证实源 NotFound，该计划仍保留目标。正常日志和最终报告明确记录 Incremental、Preserve 及本轮时间基准。

删源迁移固定保留目标：DeleteSelectedReady 与基于源缺失反向清理目标不能混用。它只删除本轮已就绪的源项，源消失正是预期结果；即使另行确认了源 NotFound，也不能据此清理已迁移目标。若用户同时显式要求这种目标镜像行为，计划应拒绝冲突配置，不能静默改变其含义。

需要在 ClickHouse 保存代次描述：以作业命名空间、job ID 和 execution_id 标识，每轮记录结构化任务类型、解析配置后的有效策略及实际决策，不仅保存原始命令文本。记录独立于 base，删源任务清空 base 后仍能查询上一已开始迁移。原始命令行只作脱敏审计；普通检查／扫描既不能假装生成了复制确认事实，也不能因它是“上一条命令”就覆盖应参考的上一迁移策略。

每轮开始前确认保存已接受计划，准备阶段和终态按同一执行身份更新；这是一轮少量状态写入，不是逐文件入库确认。未接受的语法错误等请求不改变“上一迁移策略”；接受后的失败／取消保留其已声明的源清理策略和准备状态。写入确认丢失时按同一身份确认结果或失败退出，不能在策略是否持久化未知时先启动删源。

策略查询取上一已开始迁移及其基线状态，不能只取最后成功代次；最后成功基线的提交标记另行保留。执行修订必须防止迟到的开始／运行状态覆盖终态；跨执行先后由合法的执行所有者及代次次序保证，不能把 ClickHouse 的普通查询、机器时间戳或 MAX+1 当作分布式锁。db 对上层返回统一的代次上下文，CLI／Web 不分别选择“哪个表哪条命令算上一代”。

将目前混合源／目标、原始过滤字符串、文件清单及传输开关的 request_key 拆为绑定、复制契约和选择描述，不能因为 filter 改变就直接报源／目标不匹配。相同 job ID 的源／目标绑定变化一律报错退出，检查必须先于基线清理、本轮接受记录覆盖和复制／删源调度；不能通过自动全量、重置或重新绑定继续运行。过滤范围变化在 Preserve 下允许继续比较既有目标事实。复制契约变化若要求补 ACL 等元数据，先取得并应用／校验，不能只凭旧数据成功跳过。无法解释旧确认事实时安全重建或拒绝。

在现有 migration_plan 模块集中生成任务计划，元数据观察计划作为其中一部分；用纯选择函数接收已读取的历史描述和当前结构化请求，返回计划，不在函数内部连接数据库。copy_execution 承担独占、持久化接受计划和基线准备等副作用。CLI／Web 调用相同的 app 入口，不能各自组织一次“读历史→选模式→清表”，也不引入多个相互覆盖的计划对象。

每个新执行固定一个 filter_evaluated_at：同轮所有 worker、额外确认、匹配和重试共用；新一轮重跑按新的时间计算，文件续传不冻结旧窗口，也不恢复旧扫描位置。稳定过滤定义的指纹不包含本轮时间，否则每轮会被误判为不兼容；本轮请求和报告另行绑定时间。data-mover 已提供 should_skip_at 及 DslTraversalFilter::with_time_anchor，由原生规则按显式时钟判定；app 不替换表达式字符串，也不另写比较器。稳定的 selection_key 不包含本轮时钟，续扫 resume_key 另行绑定时钟，不能跨窗口续扫。

当前依赖已有 has_relative_time_condition，可遍历 match 与 exclude 的所有分支；现有 logically_equivalent 只证明布尔表达式等价，不证明目录剪枝、缺失字段和短路求值的遍历结果等价。应复用原生有版本的遍历指纹并保留顺序，不将布尔交换律作为基线／扫描兼容证明。

  1. 严格解析当前结构化请求，取得作业独占并收束旧执行；读取上一迁移描述、基线可用性及目标实际能力。外部依赖不可用时明确报错，不猜测。
  2. 用无副作用的选择函数生成完整计划与原因：先判绑定及复制契约，再判可用确认事实与上一代是否删源，最后确定过滤、目标清理及 rename 许可。
  3. 在任何复制或删源前持久化本轮已接受计划；基线准备设为未完成。执行 Reset 或确认 Reuse 后，才标记准备就绪并启动数据流水线。解析失败等未接受请求不覆盖上一迁移策略。
  4. 重新枚举所有本轮范围，源与过滤计划在各入口一致；变化项复制，不变项按本轮校验要求复用。Preserve 下不根据缺失执行目标删除／推断 rename，也不让新路径被“相同句柄”比较吞掉。
  5. 删源任务只清理本轮命中且当前目标已就绪的项；不能遍历历史 base 将窗口外项一并删除。源缺失、权限、网络和元数据失败分别处理，不能由数据库旧确认标记单独授权。
  6. 整轮成功时提交 C；异常轮次保持 C，反复失败复用 W=1−C。对保留源端的可复用事实，重复准备不清空历史窗口外事实，也不把新路径观察升级为目标路径确认。
  7. 收束本轮写入和目录／源清理后处理基线生命周期：保留源端时保留目标确认事实；删源时按既定契约清空该 job 的 base，独立保留代次描述与最终报告。陈旧执行的延迟写入／清理必须隔离。真实网络失败、取消和未知写入结果分别验收。

二值 state 不是本轮选中证明：保留窗口外确认事实后，某个旧 current_state 经过多轮翻转可能碰巧等于本轮 W；不能用这一相等关系授权删源，也不能把所有旧 state 行当作真实源删除。源清理使用本执行实际观察到的选中项及当前目标就绪证据，保持流式和有界；需要持久化成员关系时绑定执行身份，不依赖两态标记跨轮推断。该约束与失败轮次 C／W 幂等同时成立。

复用还要求目标确认事实仍有效：本程序曾失败写入、清理或无法确认发布结果的路径，不能只凭旧成功行跳过。数据结果未知时安全重复制或由协议确定归属；版本化目标不能盲目重放已有历史。仅元数据失败则保留数据并补齐／报错，不把数据保留当作整项已就绪。

统计中只对真正完成的删除计成功；未观察、明确出界、存在性未知、复制跳过和源清理分别表达。旧确认事实数量不计入本轮 scanned／copied。若为了性能没有枚举全部旧缺失候选，则不为统计补做全量回源，也不伪报已知数量。决策模式、原因、时间基准和目标清理策略作为正常计划字段进入日志／报告；所有最终未恢复的故障进入 callback，恢复成功的错误仅进日志。

正常路径只增加每 job 的少量计划读写和一次过滤分析，不能在每个 worker 或 entry 重新查询上代命令。已观察项不重复 stat，Preserve 下不为全部窗口外事实发 HEAD；确认候选有界流式处理。真实吞吐／RSS 对照须计入新计划、存在性读取、目录收尾、异步入库和基线维护，不以牺牲事实保留或错误上报换性能。

建议实施顺序：先修复所有入口的严格过滤解析，建立统一计划和决策表；再拆分绑定／选择／复制契约并实现 Preserve 下的确认事实复用及新路径复制；随后接入按需源存在性确认、目标受保护操作和原生固定时钟；最后接入本执行选中项的删源授权、基线收尾及统一报告。结构调整与行为修改分开提交；每一步在 CLI／Web、本地／远程当前入口逐项验收，不以只新增枚举类型代替实际执行语义。

验证矩阵：逐项覆盖上代保留／删除 × 本代保留／删除 × 完成／失败／取消；时间窗口进入／离开／重入及同轮跨阈值；match／exclude／剪枝／过滤语法错误；新旧路径及硬链接多义；源存在／NotFound／权限拒绝／闪断／持续断连／静默超时／取消；S3 最新状态与历史版本；新路径已有目标／已移动但未确认；CLI 与 Web 相同输入的计划一致；CH 单机／集群、旧执行延迟清理及整轮性能。用可控时钟验证时间场景，真实路径验证协议故障，不能用 mock 或既有 source-policy 测试冒充本方案已通过。

当前实现与新增方案分开：源码已实现上一代删源后重新全量、C／W 幂等及确认路径与观察分离；尚未接入本节的独立目标清理策略、时间窗口下确认事实跨轮保留、相对过滤统一时间、按需源存在性核验及全部入口的统一计划。filter 解析入口已严格传播原始错误；保留事件已接入有界通知、累计计数、ClickHouse 归档及搬迁的缺失目标保留分支。真实 Single／双副本和 HTTP 204 验证 20 条确定性历史观察与 1 个目录按 2 个 entry 交付、计错及删除数均为 0，目标与 21 条 base 事实保留，最终报告可查询；历史源是确定性观察，不代表真实 S3 协议。request_key 仍混合多个用途，统一计划和存在性确认等仍待实施；整轮性能／RSS 未验收。

3.3　统计：扫描、目标完成与收尾分别展示

扫描、复制、校验、入库、失败及跳过计数均以 entry 为单位：一个版本化源 entry 无论含 1 个还是多个版本，在相应阶段最多计一次，不展开成版本计数。数据量仍按实际计划复制的数据累计，不能用入库历史行数增加文件／entry 数。

扫描完整前，不估算完整总量；部分成功时保留准确成功事实。即使数据传输达到 100%，仍应展示“正在校验”或“正在恢复目录元数据”。完整字段及异常示例见统计与状态呈现。

异常增量后的 rename：状态幂等，观察与目标路径分开

精确复现前提：先全量成功；下一增量必须已经比较选定文件或目录，并查询确认该项 current_state 已改变，再异常退出。之后 rename 的必须是这同一项。对尚未比较的项 rename、只改内存状态或随机中断，都不能代替本例。多轮异常／rename 继续作用于同一稳定源身份。

事实用途与推进条件
已提交代次 C只在整轮成功时推进。开始复制不改 C；失败、取消及重复启动均保留它。
未提交代次 W = 1 − C同一失败基线的所有重试复用 W。开始时幂等清除未确认路径观察，将已确认路径的扫描标记回置 C；本轮看到才标 W，不以反复翻转状态模拟新代次。
目标路径确认 copy_path_confirmed表示目标路径已由复制／rename 成功结果确认，供后续增量比较。新观察路径不能仅因进入 base 就取得该标记；继承确认须匹配路径、版本及可用源身份。此标记不等同于完整目标就绪，也不是本次源删除的入库门槛。
当前源观察本轮完整枚举得到的路径、稳定身份及元数据；与已确认目标的缺失路径关联，不能将前轮尚未执行的 rename 路径当作目标位置。

关联方向明确为“已确认旧目标路径 → 当前源路径”。按稳定身份取得唯一关联，不依赖 ctime 排序、混合历史记录恰有两条或某次旧 state 值。没有待执行 rename 的当前观察，或新路径已完成复制确认时，旧路径按删除候选处理；路径被另一身份占用时先复制，不能覆盖旧事实后假装 rename 已完成。本轮已复制的新目标不能再被旧路径覆盖。多义／冲突关联返回有类型错误并明确上报，不能仅写日志然后静默遗漏。

目标旧路径已消失可能是上轮物理移动成功但记账未完成。恢复时从当前源路径重新复制，按所选校验确认，不直接相信现存新目标数据。父目录只有实际移动成功后，其子项才可跳过物理 rename；只在计划中、执行失败或降级创建目录，都不能证明子树已经移动。

删除源端的增量也必须处理 rename，只跳过由源缺失产生的反向目标删除。完成目标 rename／恢复复制后，源清理仍遵循统一目标就绪条件，不能在 rename 分支提前直接删除源对象。

实现边界：当前使用有类型错误阻止多义关联猜测，自动处理任意硬链接多义关联仍需扩展。真实 ClickHouse 回归覆盖单机／双副本、文件／目录及多次异常后的状态与关联；完整进程 SIGKILL、真实 NFS／CIFS 身份和整轮 callback 仍按故障矩阵单独验收。

3.4　多版本：有界分段，同一对象串行推进

不建议将全部历史版本放入单个 entry。版本数量很大时，会增加内存占用、首条交付延迟和失败重放成本。保留有界历史分段，沿用路径固定分派机制。

  • 同一对象按源端明确提供的历史顺序处理，不按 version_id 字符串排序。
  • 同一对象同时最多有一个版本处于提交阶段，不同对象并行执行。
  • 某版本数据复制／发布失败或结果未知时，阻断该对象后续数据版本发布。单独源元数据获取失败不阻断按历史顺序继续复制数据；逐版本保留元数据失败，整 key 不得确认完整就绪或清理源历史。
  • 本次运行内按已确认版本事实进行有界重试；上一代保留源端时失败后可增量，重新枚举并核验已发布版本；连续删除源端时重新全量，不从扫描版本边界续扫。版本化目标写入响应丢失时先核实，不能盲目重放并生成额外版本。
版本化源的复制范围与删除范围
目标实际能力复制行为启用删除源端时
非多版本目标只复制最新可见数据版本及其约定元数据，不依次覆盖历史版本。最新记录为 delete marker 时，投影为目标对象不存在，并确认该状态，不能回退复制更早数据。最新状态完成校验、目标发布／不存在状态确认以后，永久清理该 key 的全部源数据版本和 delete marker。
多版本目标按源端明确的历史顺序复制全部数据版本及 delete marker，保存源／目标版本映射。该 key 的全部历史在目标完成校验、发布后，永久清理该 key 的全部源数据版本和 delete marker。

目标是否保留多版本由已连接目标实例的实际能力和版本配置决定，不能只按 backend 类型推断。源端版本 ID 与目标新生成的版本 ID 分别记录，不要求相同。未启用删除源端时，两种复制路径都保留源历史。

ClickHouse 内容范围与目标复制范围一致

目标ClickHouse 中的迁移记录entry 计数
非版本化目标每个 key 只保留最新版本／最新状态及所需元数据。最新源版本 ID 是比较字段，不能作为累积保留旧源版本的理由；最新为 delete marker 时记录最新不存在状态，不回退保存旧数据版本。一个实际交付并纳入该迁移阶段的 entry 计一次，不因源有很多历史版本增加次数。
版本化目标保留实际复制的各历史数据版本与 delete marker、源／目标版本映射、历史顺序及对应元数据结果，并关联其 entry 身份。一个 entry 即使对应多条版本记录，阶段完成仍只计一次；部分版本完成不能把整 entry 提前算作完成。

非版本化目标必须在数据库投影和写入之前选择最新状态，扫描临时记录、迁移基线与 entry_snapshot 都不能携带完整旧历史，再仅靠查询过滤隐藏历史。后续增量的新最新版本替换该 key 的最新事实，不按不同源 versionId 累积源历史记录。

版本化目标按每个实际复制版本持久化对应事实，snapshot 应表示对应版本，不能把整个历史容器在每条版本行重复保存。存储行需要表达 entry 与版本的关联；统计由 entry 阶段事实推进，不能通过 count(*) 推导迁移 entry 数。

非版本化目标启用删除源端时，ClickHouse 只增加按 key 的全部历史清理授权、状态及必要汇总，不另外持久化全量源历史版本清单。具体版本 ID 在清理时从源端有界流式获取和删除，下一删除代次重新全量列举当前剩余历史；不因源端要删全部历史而将旧历史灌入数据库。

复制范围与删除范围明确分开：非多版本目标仅保留最新状态，但源端仍清理全部历史；多版本目标保留全部历史，再清理源历史。清理范围限定于本 job 已纳入迁移的 key，不扩展为整个 bucket 或被过滤 key 的清空。

上一代保留源端时，下一代删除源端的增量路径必须覆盖未变化对象：已复制且源端未变化时跳过数据传输，但仍需确认当前目标就绪、复核源身份并删除对应源项；不能因没有产生复制任务而漏掉源清理。上一代已删除源端时，新删除代次重新全量，避免依赖可能缺失的迁移记录。

非空且 key 以 / 结尾的对象

对象存储中的 key 尾部是 /，并不意味着对象没有数据。扫描需保留原始 key、真实对象大小及对象身份，结合目标存储模型决定行为，不能仅凭后缀将非空对象折叠为目录标记。

目标复制与扫描行为源清理及上报
非对象存储若实际选择复制的对象 key 以 / 结尾且大小大于零，自动忽略该对象，不创建对应普通文件、不读取其内容，也不为其追加无用途元数据请求。若同前缀还有其他对象，仍正常枚举和迁移它们；需要时可为子对象创建目标目录。这是计划内跳过，不是复制错误。该 key 不取得成功迁移或源清理授权，源数据及全部源历史保留；callback 和统计明确跳过数量、已知字节及原因。
对象存储正常复制非空对象及计划要求的元数据，精确保留末尾 /，不能去掉斜杠或只创建零字节标记。非多版本目标仅复制最新状态，多版本目标按历史复制，均遵循既定版本策略。按实际复制、所需元数据、所选校验及目标持久性判断就绪，入库独立统计；满足全部源清理前置条件后才可永久删除该 key 的源历史。

例如对象 bucket 中 a/ 的内容为非空数据，同时存在 a/file.txt：迁移到 NFS 时只跳过 a/ 这个对象，a/file.txt 继续复制；迁移到另一个对象存储时，a/ 的非空内容与 a/file.txt 都应保留。目标目录删除或源前缀清理不能顺带删除被跳过的 a/ 源对象。

任务事件使用 CopySkipped 区分跳过与成功／失败，报告单独累计 skipped_count。callback 中的 copy_skipped 明细在 HTTP 2xx 后清除，累计跳过数保留；版本历史不按版本数放大此计数。跳过事件不写入复制成功基线，也不授权删源；全量、增量及双进程分类使用同一目标表示能力判断。当前实测范围以实验室说明为准；扫描前置裁剪额外元数据读取及已知跳过字节的展示仍需单独验收。

此规则在扫描 plan 中列为按 key 后缀和实际大小决定的目标适配策略，并在枚举后、额外元数据读取前应用；元数据尚未取得不应影响该对象已知的跳过判定。零字节目录标记按其既定规则处理，不将“非空尾斜杠对象自动忽略”扩大为所有以 / 结尾的 key 都忽略。

验证证据：隔离真实 S3 代理把非空尾斜杠对象及旧版本 tags 端点设为拒绝访问，实际无多余请求；尾斜杠场景只有子项和空标记的 2 次标签读取，20 版本场景仅对最新版本读取 1 次、20 条历史记录仍保留。原有源 tags 拒绝测试仍交付 20 版本数据、按 1 个失败 entry 统计并通过 HTTP callback 交付 20 条具体原因。另有原生 unordered／blocks、过滤用途及版本范围组合测试；这些证据不代表整轮吞吐／RSS 或统一断网恢复已通过。

版本化源到非版本化目标时，仅对最新可见数据版本获取计划要求的元数据并入库，不为不复制的旧版本额外读内容、ACL、tags 等。启用源删除时，清理阶段从源端流式列举旧版本身份，不将其作为历史迁移记录落库。版本化目标则对每个实际复制的数据版本获取对应元数据，delete marker 不发无意义的数据版本元数据请求。

“值为空”“不支持”“未请求”“请求失败”必须区分。源端没有可迁移的目录 mtime 时，不能用默认时间冒充源值；必需元数据获取失败不能静默变成 Omit。

源元数据获取结果与数据读取准入分开。ACL、xattr、tags、mtime、ownership／mode 等获取失败时，保留失败类别、原因及已知源身份，并继续复制可读取的数据；缺失值不能被解释成清空目标属性或写入默认权限。若定位源对象或实际数据读取本身也失败，则按真实的数据读取错误处理，不能伪报复制成功。

扫描仍须交付可执行数据复制的 entry，而不是因单个元数据观察失败丢弃对象或停止整条数据流水线。data-mover 需要将“数据传输／发布结果”和“元数据获取／应用结果”分别返回；源元数据缺失不能在数据传输开始前触发全项拒绝，也不能只靠 app 捕获异常后声称已经完成数据复制。

单个对象 ACL 等元数据获取失败，与已识别的存储网络中断分开分类。前者在数据仍可读时继续数据复制；一旦确认是源、目标或 ClickHouse 网络中断，优雅退出策略优先，不能为继续数据复制而持续发出失败请求。

plan 的需求与可读说明由任务层统一确定，能力查询、请求分组、扫描观察及后续应用归 data-mover，协议获取细节归客户端。CLI／Web 共用同一计划与成本说明；不能让各 worker 再各自推断类别或重新回源。

增量元数据比较覆盖计划要求的 tags、NFS ACL 及其他属性。ClickHouse 保存成功获取的元数据原值（raw）和分类摘要，不再采用“大 raw 只存摘要、复制时重新查询源端”的策略。原值用于比较结果交付、元数据应用及收尾，摘要用于快速筛选和定位变化类别。

扫描阶段取得一份与源身份／版本绑定的原值，同时生成对应摘要并入库；失败类别保留真实失败状态，不伪造默认原值。增量比较查询既判定变化，也在同一返回结果中按后续需要带出旧／新原值或原生 snapshot 及身份，避免比较结束后再按 key 发起第二次原值查询。当前 entry 已持有的原值可直接共享，不为复用而重复序列化或查询。

可先在数据库端利用摘要筛选变化集合，再于同一比较查询中返回这些对象所需的原值；无变更对象无需向应用批量回传大型 raw。复制与目录收尾消费比较结果携带的原值，不为取得相同 ACL／xattr／tags 再查 ClickHouse 或回源。必要的源身份一致性检查、读取失败后的重试和新一轮增量扫描仍按既定规则处理，不能与常态重复取值混为一谈。

原值较大时，以唯一原值载体、压缩编码和有界读取控制成本，而不是删掉原值。可使用 entry_snapshot 承载对应 entry／版本的原生事实，避免同时在独立 raw 列、snapshot 及每条历史行重复存同一 payload；摘要和必要索引字段独立投影。版本化目标每条记录只包含该实际复制版本，非版本化目标仍只保存最新状态，不因存 raw 扩大历史入库范围。

目录原始 mtime、mode 和 ACL 等收尾原值在扫描时捕获，正常路径共享该观察并异步入库，收尾不能重读已因子项删除改变的时间。入库缺失或进程崩溃导致无法取得原值时，要明确报告目录元数据未完成，不能伪造原值或成功；不为记账完整性增加逐文件确认。

采用条目数与字节双重约束的批次、按需投影及流式消费，避免把全部大型原值常驻内存。验收需同时证明比较结果能直接用于后续复制、没有额外原值查询、原值没有重复保存，并保持整轮性能和内存与优化前相当。

不建议对整个序列化 entry 求一个 hash 作为所有变化的判据。路径、执行身份、统计、采集来源等不是可迁移元数据语义，atime 等易变值也不应无条件导致重复更新。分类摘要能定位变化的类别，并只调度需要的元数据操作。

3.5.2　摘要契约：按语义规范化，观察状态独立保存

  • 使用稳定算法，例如仓库已有的 BLAKE3，摘要可按二进制 32 字节保存，避免不必要的十六进制膨胀。hash 格式版本、类别、编码和字段选择规则须参与摘要定义。
  • tags 和 xattr 按稳定键顺序编码，保留二进制值、字段边界及长度，避免返回顺序造成假变化。ACL 使用保持语义的规范化规则，尤其不能任意排序 NFSv4 ACE；无法安全规范化时保留有序编码。
  • 每类分别保存 Value、空集合、NotRequested、NotApplicable、Unsupported、Failed 等状态；失败或未获取不能生成一个“空 hash”并据此判为未变化。
  • 必需类别获取失败时保留元数据错误并按预算重试，数据可读则继续复制；最终未恢复时任务不能报告完整成功。只在两次观察覆盖范围一致、成功且摘要契约一致时判断未变化，缺失或失败摘要不能等同于未变化。
  • 源端变化检测比较“当前源观察”与“上次成功同步所对应的源观察”。目标回读则比较经过 UID 映射、ACL 转换和时间精度处理后的期望值，不能直接要求跨 backend 的源 hash 与目标 hash 相同。
  • hash 相同是摘要层面的相等判据，存在碰撞风险；删除源端仍需数据复制成功、所选 quick／full 校验通过、目标发布及所需持久性确认。元数据摘要相同不能直接授权删除，也不能冒充 full 模式的数据内容校验。

3.5.3　扫描执行：按 plan 合并额外读取，复制阶段复用

存储分类与接口合并是两个独立优化。把原值换成 hash，只能直接减少数据库传输或存储；如果后端不直接提供可信元数据摘要，计算本轮 ACL／tags／xattr 的 hash 仍须读取对应原值。

  1. 任务层在扫描前合并过滤、增量比较、复制和校验需求，结合源、目标实例编译 ObservationPlan；剔除无用途类别，明确保留类别的额外读取成本。
  2. 优先复用 listing／stat 已返回的 inline 事实。data-mover 根据 backend 能力组织读取，不让 app 为每个类别再次独立 stat。
  3. 扫描阶段执行所有计划要求的源元数据读取。能在同一协议请求中返回的属性合并读取；必须分开的请求有界并发，并共用故障预算与取消域。
  4. 扫描交付原值、摘要及失败状态并按目标版本范围入库，增量比较一次带出所需原值供复制和收尾复用。复制阶段不为相同 ACL／xattr／tags 再取原值；扫描重试、源变化重新观察和失败后增量扫描仍需可追踪。
  5. 跨请求观察不等于原子快照。需绑定源身份，并核验足以覆盖相关元数据类别的变化证据；不能仅以数据版本相同保证 ACL／tags 同时未变化。

S3 对象复用 LIST／HEAD 已返回的事实，避免重复 HEAD；按计划补取所需对象属性和 tags。HEAD 与 GetObjectTagging 是不同 API，不能承诺一次请求拿齐。PutObjectTagging 可修改已有对象版本的 tags，因此仅凭数据版本／ETag 不足以跳过 tags 比较。
其他 backend利用实际实例能够批量返回的属性集合；统一观察接口可封装多个必要协议操作。“一次上层 observe 调用”不等于“一次网络请求”。应报告真实 RPC 数、字节、延迟及正常路径成本。

只有 backend 明确保证某个廉价变化标记覆盖所需类别，才可用该标记跳过相应原值读取。size／mtime 一样不能证明 ACL、xattr 或 tags 没变。没有此类保证时，要严格识别这些类别的独立变化，就必须每轮观察它们；hash 无法消除这部分 IO。

大 ACL 或 xattr 随 listing 批量返回可能降低每页条目数并增加带宽，因此合并方案按实例能力和实测成本选择，不默认把全部元数据塞进每个目录页。

这里限定的是源元数据观察：目标元数据回读和 full 模式的数据内容校验仍在目标写入后的相应阶段执行，不可能前移为源扫描的成功证据。必要的源身份一致性检查也须在计划中明确，不能借此隐式重新读取整套源元数据。

协议依据：NFSv4 GETATTR 属性 bitmap、NFSv4 ACL 属性、S3 HeadObject、GetObjectTagging 和 PutObjectTagging。

3.5.4　增量确认：分类比较，成功后才推进同步基线

比较按“内容判据 + 各元数据类别”分别进行。数据无变更证据而 tags、NFS ACL、xattr 或其他必需属性发生变化时，生成元数据更新任务，并携带变化类别集合。mtime 等弱内容判据变化时，是否能只更新元数据取决于是否另有可信内容证据，不能直接跳过数据检查。

目录同样参与 ACL、ownership／mode、时间及支持的其他元数据比较，不能只比较目录标记。更新计划应处理字段删除、空集合和继承等语义，并在应用相互影响的 mode／ACL 等操作后校验最终结果。

本轮扫描观察与上次成功同步基线分开：元数据复制或校验失败时，不得把新摘要写成“已成功同步基线”，否则下一轮会把尚未迁移的变化当成无变更。仅当对应必需类别成功应用并校验后，才通过 ClickHouse 确认推进成功事实；失败类别保留待处理状态。

数据已复制、源元数据获取失败时，允许将数据传输／发布事实与元数据失败分别写入 ClickHouse，但不能写成完整对象就绪或获得删除授权。下一代按源保留策略选择全量／增量，在新扫描阶段按 plan 获取仍需补齐的元数据，后续核验已复制数据并应用、校验这些值，避免无必要地重复制数据；若 backend 修复某类元数据实际需要重写对象或历史版本，则按其能力及历史顺序处理并报告真实工作量。

示例：size／mtime 不变而 tags、NFS ACL 或 xattr 单独变化，仍必须生成更新任务。删除前所需元数据必须应用并校验成功；异步入库完成与否独立统计。

3.6　网络中断：先做有界防抖确认，确认后尽早退出

单次超时、连接重置先进入 suspected，短确认窗口复核实际依赖；稳定恢复后继续，持续失败才进入 stopping 并以网络错误收尾。下一次任务按上一代源保留策略选择全量或增量。

  1. 所有扫描、元数据读取、传输、发布、数据库及删除操作具备有界请求等待。断连和静默丢包／超时分开记录检测耗时；批处理、空闲和背压期间也需有界感知故障。
  2. 首次疑似网络故障先暂停相关依赖的新调度与源删除准入，不把部分数据或未知提交当成成功，也不立即发出终态失败 callback。
  3. 同一依赖的并发错误合并为一次故障事件，用少量有界、无业务写入副作用的真实存储／数据库请求或既有请求结果复核。不能仅凭 ping、一次 TCP 建连或一条请求成功就认定全部业务已恢复；失败操作及未知副作用还需对账。
  4. 窗口内满足 plan 稳定恢复条件后，按副作用证据安全继续；仍未知对象保持单独阻断与对账，不能解除其删除限制。该次短抖动只写日志。若仍失败、反复抖动未达到稳定条件或窗口耗尽，确认中断；事件首次异常时间不因其他请求重置。网络确认不要求在窗口内完成整文件重传。
  5. 确认中断后立即停止新工作、预取和排队消费，传播取消并永久关闭本次执行的源删除准入。不能继续处理队列或再启动长重连循环。
  6. 按协议能力取消在途请求或等待其在受控期限内收束，回收 worker、连接与后台任务。进度线程、查询任务和收尾任务也随执行结束，不依赖无限等待某个阻塞调用返回。
  7. 已获确定证据的操作保留成功事实；已发出但未能确认的写入、发布、ClickHouse 提交或源删除记录为结果未知，不能因取消或超时改写为未执行。已确定的数据复制失败进入对应目标清理，网络使清理无法完成时记录待清理／未知，不持续重连等待。
  8. 在可用 ClickHouse 中异步保存事实和最终报告，callback 准确区分业务完成与数据库缺失。数据库持续不可达按预算停止新调度、收束在途操作；已就绪并删除的对象不回滚，不为保存记录无限等待。
  9. 发送最终 callback，按受控超时与既定重试上限收尾，实际未交付则明确记录发送失败；全部后台操作收束后退出，不能把前台返回当作后台已经停止。

探测并发、频率和持续时间有界，同一依赖共享事件与确认结果，防止 worker 各自判定引起探测风暴或相互反复暂停／恢复。权限、认证、只读、限流等按实际类型处理，不能全部当成断网；防抖也不能成为无限等待网络恢复的理由。

日志记录完整故障、取消传播、收束和发送过程。callback 端点本身因断网无法接收时，不能承诺送达；按已有失败载荷规则留存可查询证据。最终报告必须区分“迁移已失败”“通知待交付／失败”和“数据库事实未确认”。

3.7　偶发失败：按阶段重试，仅最终未恢复错误进入 callback

可重试的单对象错误、限流等，可在次数与总时间双重限制内退避重试并加入抖动；权限错误、不支持的必需元数据、无效配置不应持续重试。疑似网络故障只在统一短确认窗口中复核／有限恢复，确认持续中断后直接优雅退出，不在单对象重试循环中再等待网络。源对象变化时重新观察或报告冲突。

重试单位为“对象的具体阶段”。目标数据已确认发布后，单独源元数据获取失败应重试元数据阶段，后续清理或记账失败也不应触发无必要的整文件重复制。历史前序数据发布失败／未知时阻断后序数据发布；单独元数据获取失败不阻断可执行的数据复制，但必须保留未完成状态并阻断源删除。

每次失败、退避、重试和最终恢复结果都写入日志，并保留任务、执行、对象、版本、阶段及实际原因。预算内恢复成功的错误不进入 callback 错误明细、current_error 或累计错误计数，也不回放到终态 callback；重试期间可展示 recovering 阶段及尝试进度，不提前发送仍可能恢复的错误。

不可重试的错误、重试预算耗尽仍失败的操作，以及退出时仍无法确认结果的操作，必须形成最终错误进入 callback。覆盖初始化与计划准入、扫描、全部元数据获取／复制、数据复制、校验、目标发布、ClickHouse、源端删除、目录收尾及取消过程中的实际收尾错误；不能只记日志、只报首个原因，或只增加一个没有明细的总数。正常取消状态与取消期间发生的实际错误分开表达。

callback 是外部 HTTP 接口，HTTP 2xx 即接收成功，无需返回 batch_id 或特定响应体；3xx 不视为成功且不自动跳转。每批成功后清理该批待发错误明细，累计 entry 错误数和任务错误数始终保留。ClickHouse 的内部确认只表示发送方已记录该批 HTTP 接收结果，避免重发，不表示外部业务已处理完成；确认写入失败不能将同进程已经收到 2xx 的明细再次主动发送。崩溃发生在接收与确认之间仍可能重复，外部按事件身份幂等。

实现按最多 64 条归档前缀与分页读写，通过持久化和背压控制内存；内部待确认记录最多 128 条，未知归档前缀最多 64 条。未恢复 checkpoint 且无错误时无需访问诊断表，不增加源端元数据读取。最终明细可分批发送，再以无明细汇总报告的 diagnostics_complete 表示完整性；预算耗尽、遗漏或确认未完成必须为 false。分批终态报告序号递增，接收端不能仅因已收到首个终态就忽略最后汇总。

终态载荷须明确实际任务状态、全部最终错误累计数及错误明细交付是否完成；未发送完的明细保留为待交付，不得宣称 callback 已完整送达。callback 自身发送失败的原因只记录日志，不写入 ClickHouse，也不能递归触发无限错误通知。

终态 callback 首次失败后最多再重试 3 次；准确最终报告及任务／执行身份独立保存到可用 ClickHouse，供外部应用查询；不以 callback 是否配置或投递成功作为保存条件。发送失败原因只记日志，不入库，HTTP 2xx 后仍保留报告原文。通知失败不改变任务实际结果，也不能标记为已交付。ClickHouse 与 callback 同时不可用时由上层处理，不增加专门兜底存储。

04 / MOVE删除源端的全量迁移

对应问题：逐文件删除、目录删除时机、故障安全、校验、统计、blocks 与删除失败。

4.1　目标就绪后删除，ClickHouse 异步入库

用户确认接受异步入库最终失败导致的少量迁移记录缺失。删除资格来自目标副本就绪，单项 ClickHouse 确认不再是删除前置条件；不以小概率记账失败降低全量正常吞吐。

统一删除准入：所需数据复制成功、元数据应用及校验成功、所选 quick／full 校验通过、最终发布及 backend 所需持久性确定、执行与源身份有效，且未取消。任一未解决数据／元数据错误阻断相应对象；版本化源任一所需版本失败阻断整个 key 的历史清理。数据库入库结果独立处理。

  1. 观察源对象

    捕获身份、版本及所需元数据，绑定本轮计划。

  2. 复制并校验

    完成数据；quick 校验元数据，full 还校验内容。

  3. 确认目标就绪

    完成元数据、发布及所需稳定写入，结果确定。

  4. 复核并删除源端

    确认源身份、执行及取消状态，调用受保护删除。

  5. 异步批量入库

    目标事实及删除结果有界排队，不等待单项确认。

  6. 独立记录结果

    搬迁与入库分别计数；最终数据库错误明确上报。

目标就绪事实可以在删除前进入异步队列，但源删除不等待该批落库。队列按条数及字节有界；背压和任务级故障仍可停止新调度。正常结束收束写入，持续故障有界退出，不无限等待，不回滚已安全完成的搬迁。

4.2　目录原值、目标收尾与源空目录清理

  1. 扫描时捕获源目录原始 mtime、mode、ownership、所需 ACL／xattr；当前执行复用原始观察并异步入库，不能在子项删除后以重新读取的时间替代原值。
  2. 目录后代复制完成、目标命名空间修改结束后，应用并校验目标目录最终元数据；blocks 顺序本身不构成 worker 完成屏障。
  3. 对应后代处理已结束、源目录为空、目录目标元数据就绪且没有未知操作时，从深到浅受保护删除空目录；迁移根默认保留，不等待目录事实入库。
  4. 目录结果异步记账。若中断且未入库导致原始目录元数据不可用，明确报告目录收尾未完成，不伪造原值；不为记账缺失新增逐文件确认或专门持久化回执。

失败、过滤、新增或未枚举内容保留；源目录非空不能升级为递归删除。普通文件可在自身目标就绪后删除，目录按真实后代完成状态收尾。需要保证目标整树先就绪的模式，应使用明确的子树完成屏障，不能由扫描顺序或数据库写入顺序推断。所有跟踪状态必须有界。

故障／异常源端处理恢复与上报
源数据读取最终失败保留源文件。若本次已产生目标数据，清理对应失败产物；尚未写入则不删除其他已有目标。按阶段准确报告数据失败与清理结果。
源元数据获取失败，数据仍可读继续数据复制，保留源对象；版本化源阻断该 key 的全部历史清理。数据与元数据结果分别入库；预算内恢复仅记日志，最终未恢复在 callback 明确提示“源端元数据获取失败”，不能标记完整校验成功或删除授权。
目标数据写入最终失败保留源文件。依据本次写入／stage 身份删除对应失败数据，失效相关续传状态；清理失败或未知也进入 callback，不确认目标就绪。
full 模式内容校验最终失败保留源文件，版本化源阻断该 key 的历史清理。作为数据失败清理本次错误目标数据，不能静默降为 quick 放行。
仅元数据复制／校验失败保留源文件，禁止删除授权。保留已复制目标数据，记录失败类别与待补齐状态；后续增量按能力修复元数据，不按普通数据复制失败清理目标。
数据失败后的目标清理失败保留源文件。分别记录原始数据错误和清理错误，残留标记为待清理／未知；下一次增量先处理残留，不能将失效断点继续作为正常续传。
任何数据／元数据复制或校验错误保留对应源对象；版本化源阻断整个 key 的清理。预算内恢复仅记日志；最终未恢复必须在 callback 明确上报。恢复后重新满足目标就绪及身份检查即可删除，不等待单项入库。
发布超时／响应丢失目标结果未确认前不删除。标记结果未知，核对发布身份及最终对象；版本化目标禁止盲目重放。
未确认目标持久性保留源文件。等待 backend 所需的稳定写入／提交证据，读回一致本身不足以替代持久性。
目标就绪后源端断网经防抖确认持续断网后，停止新工作与源删除。优雅退出并 callback；下一删除代次重新全量处理当前源端，已有目标不会仅因源端缺失被删除。
删除超时／响应丢失不盲目再次删除同一路径。标记删除结果未知，重新观察源身份并对账。
源路径被新对象替换保留新对象。报告身份冲突；原对象的迁移证据不能授权删除新对象。
目标被覆盖／身份改变暂停尚未执行的删除。旧就绪证据失效，重新核验或报告冲突。
ClickHouse 未启用不把缺少逐文件入库作为删源障碍；目标就绪门槛不变。明确无数据库时缺少持久基线／报告和代次证据，默认全量；目录收尾等不依赖数据库的能力仍须实际实现，不能据本方案声称已经可用。
ClickHouse 不可用／写入失败已就绪对象允许先删除；确认持续故障后停止新调度并有界退出，不回滚已完成搬迁。最终未恢复数据库错误进入 callback，允许记录缺失；保留源端的后续增量可重复制，连续删除代次重新全量。
ClickHouse 确认丢失／超时不撤销已成立的目标就绪与删除资格。同一幂等身份进行有界批量重试，入库结果未明不能计作已入库；已删除源项的记录允许缺失。
删除成功后记账失败／崩溃保留目标副本，不回滚搬迁。接受缺失记录；下一删除代次全量处理当前源端，不新增目标对账或补记系统。缺失源项不会触发目标删除。
源只读／权限不足保留源文件和已就绪目标。标记清理失败；原因消除后复核身份，仅重试删除。
指定版本删除失败／受保护保留未成功删除的源版本。按版本报告权限、Object Lock、保留策略或 MFA 等原因；不能退回不带版本 ID 的逻辑删除，也不能自动绕过保护。
版本永久删除响应丢失只对原源版本身份对账或重试。查询指定版本及版本清单，不能以当前 key 的 GET 返回不存在判定历史版本已删除；不得误删同 key 新增的版本。
用户取消停止新删除。收束在途操作，保留已发删除的实际或未知结果。
旧执行未停止／并发接管不允许新执行继续删除。先收束旧执行，确认身份和副作用，再允许接管。
目录非空／枚举不完整保留目录及残留项。报告未完成、过滤保留或并发新增，不升级为递归删除。

NFS 的目标就绪必须包含 backend 对所需稳定存储的确认，不能只依据客户端缓存或回读一致。稳定写入与 COMMIT 的协议处理归客户端和 data-mover，见 NFSv4 COMMIT 语义。

历史版本、软链接、归档同样先确认目标就绪再受保护删除，异步记账。归档发布不能直接授权递归删除源目录；逐项依据已校验清单和源身份清理，保留新建、变化及未纳入清单的对象。

4.4　校验：默认 quick，仅显式 full 校验数据内容

默认快速校验（quick）仅校验元数据。通过命令行参数显式要求全量校验（full）时，同时校验文件数据内容与元数据。此规则同时适用于保留源端和删除源端，删除模式不再隐式强制 full。

模式选择与范围删除前要求
quick（默认）未开启全量校验参数时采用。比较类型、大小及计划要求的 mtime、mode、ownership、ACL、xattr、tags 等元数据；不做文件内容哈希比对或为内容验证额外回读完整文件。数据复制成功、全部所需元数据校验通过、发布及所需持久性确定，不等待单项 ClickHouse 入库。
full（显式）以现有 --enable-integrity-check 参数作为显式选择入口，语义为内容校验加全部 quick 元数据校验；具体实现仍待修改。除 quick 的全部条件外，所复制数据版本的内容校验必须成功，才能取得完整就绪事实并进入删除流程。

CLI、配置解析和 Web 任务契约统一输出明确的 verification_mode。未指定全量校验时默认 quick；不能将旧布尔 false 解释成完全不校验，也不能让删除路径无视所选模式强制全量内容回读。校验模式参与执行身份绑定，运行内重试和失败后增量均不能把旧 quick 事实直接冒充 full 成功。

对象／维度校验内容与时机
普通文件数据两种模式都要求传输成功。quick 对类型、长度等元数据进行比较；full 额外验证内容摘要，源摘要绑定本次读取对象，目标执行对应强度的回读或 backend 可证明的内容校验。
普通文件元数据按计划验证 mtime、mode、ownership、ACL、xattr、tags 等必需项；在删除之前完成。
软链接校验链接目标本身及约定元数据，不跟随链接校验其指向的文件。
目录后代命名空间操作结束后，恢复并验证目录最终元数据，再确认目录完成。
时间精度与读取副作用按协商精度和允许转换比较；不可设置的 ctime 不作为复制成功条件。内容回读可能改变 atime，必要时在回读后恢复最终时间，再确认元数据。

quick 校验不能证明文件内容一致，但属于本方案允许的默认删除前校验策略；不能把同大小、同 mtime 或元数据摘要相同表述为内容已验证。full 模式任何数据不匹配，以及两种模式任何必需元数据失败，均阻断对应源删除；单项 ClickHouse 未确认不阻断目标已就绪对象。不得在 full 失败后自动降为 quick，也不得为通过性能验收将 full 工作量排除在其整轮结果之外。

源元数据获取失败时，quick 对应类别的校验应为无法完成／失败，而非成功；full 仍可完成可读取数据的内容校验，但元数据缺失同样阻止整项校验通过。两种模式均应继续执行仍可完成的数据复制，并报告元数据错误，不因缺失元数据跳过数据任务。

4.5　统计：目标成功不等于搬迁完成

增加“目标已就绪”“源文件已删除”“删除待重试”“删除失败”“删除结果未知”和“源目录清理进度”。清理失败不能记为复制失败，也不能计作已搬迁完成。

源端为空不能单独作为成功依据，必须结合本轮计划和已确认事实判断；扫描未完成时，源端剩余量仍可能未知。示例及计数规则见统计与状态呈现。

4.6　扫描模式与代次选择独立，不支持断点续扫

全量采用 unordered 扫描，加全局完成屏障、目录最终元数据和从深到浅的空目录删除。不创建、保存或恢复扫描 checkpoint，不为全量增加 blocks 续扫、确认扫描块或定时保存扫描游标的机制。

上一代保留源端时，新任务可增量重新枚举；当前删除源端且上一代删除源端时，新代次全量重新枚举并清空 base。都不从扫描断点继续。文件字节级续传独立选择；源缺失不得在删除源端任务中触发目标副本删除。

本次运行内保留可重试单对象错误的有限重试、取消及未知副作用记录；已识别网络中断则立即进入优雅退出。文件传输的原子发布、分块等协议机制不等于扫描续扫，不因移除扫描 checkpoint 而省略删除前的可靠证据。

未来若单纯为了提前完成子树评估 blocks，也只涉及枚举与完成屏障，不引入全量断点续扫要求。独立扫描命令或其他场景已有的续扫规范不扩大为本次全量迁移的实现范围。

文件级断点续传；不续传固定使用 Direct

文件支持断点续传，扫描不支持断点续扫，两者独立。统一使用 sync 的 --resume 选择文件续传；未启用时固定为 Direct，不新增 --transfer-mode atomic|direct，也不提供 AtomicReplace 作为本迁移流程的选择。

参数本项目模式 / data-mover 全称行为
--resumeCheckpoint / TransferPolicy::Checkpointed使用目标支持的文件传输检查点。增量重新枚举到文件时，核验源身份、版本、传输绑定和状态，复用仍有效且未因数据失败失效的已确认部分，不恢复扫描位置。
未启用 --resumeDirect / TransferPolicy::Direct直接写最终对象，不使用 staging／原子 rename／续传检查点；中途可能出现部分内容，数据复制最终失败后必须清理本次失败产物。

CLI、Web 和 plan 统一解析为 Checkpointed 或 Direct 并记录执行绑定。当前 --in-place 等 Atomic 选择入口按新契约整理，不能无视“非续传使用 Direct”静默切换。quick／full 校验是另一维选择，两种传输模式都适用，不能相互隐式覆盖。Atomic 在 data-mover 中的全称仍是 TransferPolicy::AtomicReplace，但不属于本方案选择范围。

扫描前 plan 检查所选模式及远程传输路线的真实能力。若某 backend 的 Direct 能力尚未提供，应在 data-mover／客户端补齐后支持，不得伪装 Direct、静默改模式或绕过删除前持久性要求；未满足能力时准确报告计划错误。Checkpointed 的有效粒度和小文件是否省略检查点也需如实说明。

续传前匹配源身份／版本、目标和已持久化传输状态；源变化、绑定不符或数据已最终失败时不能复用旧断点。仍有效的文件中断状态可供下一次增量复用，但数据最终失败必须清理并失效断点，此文件下一次从头传输。两者不能混同，也不能以“支持断点续传”为由保留已经判定失败的数据。

目标清理：数据失败删除，元数据失败保留

最终结果目标处理源端与再次执行
数据读取／写入／内容校验失败清理本次失败复制产生的目标数据、stage／分段上传等产物及关联失效续传状态，记录清理是否确认完成。不删除源端；下一次增量先确认残留已清理，再重新复制该失败文件。
仅元数据获取／应用／校验失败保留已复制目标数据，记录数据完成与元数据失败，不作为整项就绪。不删除源端；下一次增量补齐元数据，避免无必要的整文件重复制。
仅 ClickHouse 入库失败／未知保留有效目标数据，不把记账错误当成数据复制错误。目标就绪即可删除源端；独立报告入库失败／未知，允许缺失记录。

预算内的调用错误尚可安全重试时，先按阶段重试；最终成功只留日志，不执行失败清理。最终确认数据失败后，两种传输模式均执行上述清理；若数据和元数据都失败，以数据失败的目标清理规则处理。

清理绑定本次执行的目标对象／版本／stage 身份，不能误删本次未修改的既有成功副本、同 key 的其他成功历史版本或其他写入方的新数据。若 Direct 已覆盖已有目标并最终失败，当前受影响数据作为本次失败产物清理，不能宣称恢复了覆盖前内容；未曾写入目标时不删除无关已有副本。版本化目标精确清理失败复制产生的版本或上传，不能用不带版本身份的删除制造新的 delete marker。具体清理动作与证据由 data-mover／客户端负责，任务层记录结果与后续增量动作。

网络中断仍需尽早优雅退出。应清理的数据在网络不可达时不可能保证即时删除：只在受控收尾期限内尝试，未确认完成就记录待清理／未知并明确 callback，随后退出，不为清理持续重连。任何被标为数据失败待清理的前缀都不能再作为正常续传依据。

4.7　删除失败：保留目标，本轮按阶段重试

源端删除过程中确认网络中断，立即停止新增删除并优雅退出，不持续重试等待重连。只读、权限不足、对象锁或保留策略限制应准确上报并停止无效重试。当前操作的安全重试只重试删除；下一代按上一代源保留策略选择模式，连续删除源端仍重新全量，可能重新复制剩余项，不要求专门对账系统。

重试删除前，复核当前目标就绪证据仍有效、源路径仍指向原对象及执行身份有效；不要求单项 ClickHouse 记录已确认。删除曾返回未知时，即使路径重新存在，也不能直接继续删除，因为它可能已经是新文件。

版本化源：两类目标都永久清理全部源历史

版本化源端的删除是对该迁移 key 全部历史记录的永久清理，与目标只保留最新状态还是保留完整历史无关。执行层逐条指定源 versionId 删除数据版本与已有 delete marker，不能新增 delete marker 代替。协议依据见 S3 DeleteObject 与 delete marker 永久删除。

  1. 按目标策略完成扫描和复制投影。非版本化目标只将最新状态写入 ClickHouse；版本化目标写入所复制的历史版本。删除源历史仍需遍历该 key 的全部源版本，但非版本化目标不因此把旧历史明细存入数据库。
  2. 非版本化目标：只复制最新可见数据版本，按 quick／full 校验该版本与约定元数据；最新为 delete marker 时确认目标不存在。版本化目标：按历史迁移全部数据版本及标记，quick 校验元数据，full 再校验所复制数据内容。不复制的旧数据只在源清理时流式列举，不落入非版本化目标的迁移历史。
  3. 确认目标策略要求的整体就绪：非版本化目标只要求最新状态成功，版本化目标要求全部所需历史成功。复核源身份后永久清理全部源历史，目标事实及清理结果异步入库，不等单项确认。
  4. 前置事实确认后，有界读取源端剩余版本 ID 并永久清理，保留当前版本／标记最后处理。非版本化目标只维护按 key 的清理状态及必要汇总，不保存历史版本行；失败后重新列举剩余历史，不依赖存储扫描游标或一次把历史加载到内存。
  5. 先清理非当前历史版本与标记，当前版本或当前 delete marker 最后处理，避免清理过程中将旧版本重新暴露为当前可见内容。当前身份变化时重新核验，不删除计划外新版本；并发源修改仍需满足既定独占或条件操作要求。
  6. 每次永久删除绑定源 backend、key 和源 versionId。非版本化目标更新按 key 的清理状态，不新增旧版本迁移行；版本化目标可更新已有历史版本的源清理结果。具体错误与操作身份按诊断契约记录，不能用目标版本 ID、当前版本或新版本代替原删除对象。

普通版本 ID 可用于精确指定删除对象；对于 versioning suspended 等情况下可能被替换的 null 版本，必须显式传递 null 版本身份，并增加相应身份校验、条件删除或独占控制，不能将字符串 null 当作不可变版本保证。

源清理的迁移主计数同样按 entry，不能按永久删除的版本条数增加。该 key 的全部源历史确认清空后，关联 entry 才能确认源清理完成，各 entry 只计一次；逐版本操作留作协议及诊断事实，不充当文件／entry 完成数。源逻辑不可见不等于全部历史已永久删除，也不证明释放了多少存储空间。

为满足“全部历史删除”，迁移与清理期间必须对该源 key 停写或取得实际有效的独占控制。若仍发现新版本或历史清单变化，停止该 key 的新增删除并报告冲突，重新迁移所需的最新状态／新增历史后再确认；不能静默保留新增版本却报告源端已全部清空，也不能未经重新确认就删除它们。

非多版本目标只保留最新状态、随后删除源端全部历史是本方案的既定迁移语义，不增加“必须先保存旧版本副本”的限制。必须准确保存目标策略和清理授权；不能把未复制旧版本记录为目标迁移成功，也不能把其永久删除统计为复制版本数。

锁定的 data-mover 已提供 transfer 与受保护 purge_observed，当前没有 move_file。复用现有职责边界，必要的版本身份校验、指定版本永久删除及协议恢复归库；app 在目标整体就绪后调用清理并异步记录结果。源永久删除与目标回放 delete marker 是不同操作。

05 / OBSERVABILITY统计与状态呈现

以持久化、已确认事实为累计统计依据，运行中状态单独展示。CLI、Web、查询接口和 callback 共用同一口径。版本化源以 entry 计数，一个 entry 内无论有多少历史版本，在每个阶段最多计一次；ClickHouse 历史行数不能作为 entry 数。

类别建议展示异常场景要求
扫描已访问、已过滤、目标不支持表示而按规则跳过、已纳入计划；目录、普通文件、软链接及真实对象分别按语义记录；扫描是否完整。非空尾斜杠对象到非对象目标时单独统计跳过数量、已知字节和原因，不计作复制失败或成功，不触发源删除，也不剪枝子对象。扫描失败时不得宣称掌握完整总量。
计划规模纳入计划的 entry 数及实际需复制的逻辑字节数。一个 entry 含多个版本仍只计一次；源历史枚举数、目标版本行数及删除请求次数不增加主计数。若历史分段交付多个 entry，各 entry 按其边界各计一次，不按 key 强制合并或按版本展开。
执行中排队、复制／校验、整体就绪、源删除、异步入库、重试及依赖恢复。删除与入库是独立进度；入库待确认不阻断已就绪对象的删除，不把短暂恢复计为最终失败。
目标结果按 entry 的数据完成、元数据待补齐／失败、入库确认、整体就绪、最终失败及未知结果。entry 内所需版本全部满足对应阶段条件才计该阶段完成；仅部分版本成功不提前加一。元数据失败可已有数据完成，但整体就绪与删除资格仍未成立。
目录收尾待处理、元数据已确认、失败；源目录待删除／已删除。数据传输完毕不等于目录完成；非空目录单独报告原因。
源端清理按 entry 的源清理完成、待清理、失败及未知结果。版本化源关联 key 的全部历史清理确认完成，entry 才计一次；删除多个版本不增加 entry 数，部分清理不得算作完成。
性能逻辑完成字节、实际传输字节、重传字节、复用字节、校验读取字节、速率与耗时。重传不增加逻辑完成字节，校验流量不冒充迁移有效吞吐。
任务与通知实际任务状态、当前阶段、完成条件、全部最终未恢复错误及其明细交付状态。预算内重试恢复错误仅留日志，不进入 callback 错误集合；最终未恢复错误不得遗漏。通知失败独立表达，不能改变迁移事实或将未交付载荷标为已交付。

正常场景

版本化 entry 示例：一个 entry 包含 20 个数据版本，目标非版本化时只复制并入库最新版本，复制完成计数为 1；目标版本化时复制并入库 20 条版本记录，复制完成计数仍为 1。若仅完成其中 19 个，entry 的完整复制完成数为 0，显示执行中或部分完成。

字节与数量分开：非版本化目标只累计最新所选数据的逻辑字节，版本化目标累计实际所选版本的数据字节；重传字节单列，不把版本数转换为 entry 数。

保留源端时可展示“文件复制与校验完成，正在恢复目录元数据”；删除源端时分别展示目标就绪、源清理及异步入库进度。只有对应阶段事实成立才增加该阶段计数。

异步入库示例：100 个文件目标已就绪，其中 80 个确认入库，20 个仍在异步队列。100 个都可在复核源身份后删除；入库确认数仍是 80，不以删除数补算。若这 20 个最终入库失败，保留目标并报告数据库错误，允许记录缺失。

清理失败场景

示例：1000 个文件在目标就绪，其中 20 个因源端只读未删除；入库进度独立展示。

计数与代次规则

  • 每个 entry 有可识别的身份及关联版本，阶段完成按 entry 去重；重试、重复广播或 ClickHouse 多行确认不能重复加一。可复用基线的增量分别展示本次处理与已知累计事实；重新全量不继承旧删除代次的累计数，重扫不重复累计，也不从扫描 checkpoint 还原累计数。
  • 同一 entry 多个版本或多个元数据类别失败，失败 entry 数只计一次，callback 仍保留全部最终错误明细。无 entry 的任务级错误独立呈现，不能伪造一个文件计数。
  • callback 错误明细及错误计数仅包含最终未恢复错误，预算内重试后成功的错误只写日志；重试期间不提前上报临时错误，也不在终态重新发送已恢复过程。执行阶段／尝试进度与错误集合分开。
  • 目标就绪、源删除确认等累计里程碑可以重叠；排队、执行中、待重试等当前状态必须按明确定义计算，不能把不同口径简单相加。
  • 扫描不完整或结果未知时，总量、剩余量和完成百分比标注不完整／未知，不做估算补偿。
  • 清理失败、数据失败、目录元数据失败、取消、未知结果与通知失败分别表达，不共用一个 error_count 解释全部结果。

实现后对受影响真实链路实施受控故障注入，至少覆盖闪断、持续断连、静默丢包／超时、恢复、取消与进程崩溃。单元测试和正常路径成功不能替代真实故障验证。

验收维度必须核对的结果
目录与元数据根目录、空目录、深层目录、限制性权限、失败后重试；文件数据完成后目录 mtime 不再被本轮操作改变；必需元数据真实读回一致。
校验模式未开启命令行全量校验参数时仅执行 quick 元数据校验；显式开启时 full 同时校验数据与元数据。验证删除路径不额外强制 full，full 失败不降级；同大小同 mtime 但内容不同的样例必须被 full 检出，quick 不得声称检测或证明内容一致。CLI／Web、恢复绑定、ClickHouse 和 callback 中模式一致。
分类元数据增量size／mtime 不变而仅 tags、NFS ACL、xattr、mode／owner 或其他所选属性变化；覆盖文件与目录、属性删除与空集合、ACE 顺序、源目标映射、获取失败及应用失败后的再次增量，确保不漏更新或错误推进基线。
源元数据获取失败分别注入 ACL、xattr、tags、时间及权限获取失败，验证数据仍实际复制且按模式检查；ClickHouse 分别记录数据成功与元数据失败，源端不删除。验证最终未恢复 callback 提示明确、恢复成功仅日志、历史后续数据可按顺序复制、失败后增量补齐缺失类别。
扫描 plan 与额外读取扫描前输出类别、用途、额外调用估算、预算及原值载体和比较返回字段；NFS→S3 无依赖时 ACL／xattr 读取为零。所需源原值在扫描获取并入库，复制复用；覆盖版本选择、过滤／映射依赖、读取失败、目标回读和 full 校验阶段。
原值与比较查询验证大型 raw 与摘要均被正确保存且未重复承载；增量比较同一次查询返回后续所需原值，复制无二次查库或常态回源。覆盖旧／新值差异、缺失／失败状态、目录原始值、历史入库范围及失败后增量，测量查询次数、返回字节、数据库存储和峰值 RSS。
摘要与获取成本验证摘要确定性、观察状态区别、原值恢复引用和目录收尾；测量每对象实际 RPC 数、请求字节、摘要与快照存储量，不能将减少 SQL 列读取声称为减少源端 RPC。
安全删除证明目标数据、元数据、所选校验及持久性早于源删除；刻意延迟／丢失单项入库仍可删除。覆盖普通文件、软链接、目录、历史、归档、源替换、只读、非空目录及未知结果。
多版本分别验证非版本化目标仅复制并入库最新状态、版本化目标复制并入库历史，源端均永久清理全部历史；覆盖最新为 delete marker、目标预存同 key、跨 entry、长历史和部分确认。覆盖 null 版本、受保护版本、删除响应丢失及源新增版本，确认非版本化目标不因清理额外落库历史，清理后源版本清单为空才完成。
版本入库与 entry 统计同一 entry 包含多个版本：非版本化目标的 base、临时迁移记录和 snapshot 只保存最新状态；版本化目标保存所复制历史及 entry 关联，但两者对应阶段完成都只计一次。覆盖部分版本成功、多个版本失败、跨批次入库、重复 ACK、重扫和历史分段 entry，验证不按数据库行数或版本数累计。
非空尾斜杠对象构造 a/ 非空对象与同前缀 a/file.txt：到非对象目标仅跳过 a/，子对象继续迁移且源 a/ 全部历史不删除；到对象目标验证完整 key、非空内容、所需元数据和版本顺序。零字节标记不误跳过，callback 跳过原因与计数准确，不将该记录计作失败或迁移成功。
代次选择与隔离保留源端全量／增量→删除源端增量；删除源端全量／增量→下一删除代次全量，含上一代成功／失败／取消及零入库事实。核验新全量清空、增量复用、旧执行隔离、无扫描 checkpoint、不因源缺失误删目标。
文件传输与目标清理验证启用文件续传为 Checkpointed、否则 Direct，不存在 Atomic 选择分支。数据最终失败后对应目标产物删除、断点失效；元数据失败和仅数据库失败保留已复制数据。覆盖有效中断续传、源变化、Direct 部分目标、失败版本精确清理、清理超时／失败和下一次增量优先清理，兼顾快速退出与准确 callback。
网络防抖与退出覆盖单次超时、窗口内稳定恢复、反复抖动和持续断网，涉及初始化、扫描、元数据、传输、发布、数据库、删除及空闲／背压。短抖动不误退出且仅写日志，确认持续中断后尽早收束并 callback；记录检测、防抖、停止调度与源删除、收束、通知及退出耗时，验证窗口不被并发或分页重置、探测有界、未知副作用不被抹去。
数据库与通知覆盖 Single／Cluster 的异步批量写入、响应丢失、写入失败及删除后崩溃，允许缺失记录而不删除有效目标。保留源端的增量允许重复制缺失项；连续删除代次全量。最终错误 callback、可用 ClickHouse 保存报告，通知失败原因不入库。
统计累计数与实际源／目标逐项核对；恢复不重复计数；重传不增加逻辑完成量；扫描不完整与结果未知准确呈现。
错误与删除准入注入数据、ACL、xattr、tags 等复制／校验错误，验证相应对象或 key 不删源；仅数据库错误独立处理，不伪装数据失败。验证预算内恢复仅日志，最终错误全部 callback，多版本失败计 entry 一次但逐版本说明原因。
性能与资源主要与固定优化前版本做完整全量迁移 A/B，性能和内存开销均应相当；分别验证保留源端与删除源端，报告整轮耗时、有效吞吐、持续及峰值 RSS、ClickHouse 开销。扫描不落库基线仅作对应模式的辅助验收，队列、批次和在途工作有界。

7.1　全量迁移目标：性能与内存开销均与优化前相当

本方案的主要验收对象是完整全量迁移，主要基线为固定的优化前运行时代码版本，不是单独的扫描吞吐或不落库扫描。保留源端与删除源端分别对比；不得用一个模式的收益抵消另一个模式的退化。

优化前后 A/B 的比较契约
维度要求
环境与工作量固定硬件、网络、源／目标 backend、ClickHouse 部署、并发和数据集，分别对 Checkpointed、Direct 做同模式前后比较；对齐源／目标初始状态及冷热缓存条件。每次删除模式运行都从等价源数据重新开始，不能因前次执行删走部分文件而减少工作量。
配置与语义默认 quick 为主要验收路径，显式 full 单独验收，同模式 A/B。保持可对齐的元数据、版本和过滤选项一致，标明旧实现缺失的新保证或强制内容回读等差异；不能将 quick 与 full 混比，也不能关闭元数据校验或目标持久性确认换取持平。
时间与吞吐从任务启动到实际终态计时，包含初始化、base 清理、扫描、全部元数据获取与摘要、传输、校验、异步批量入库收束、删除、目录收尾及任务收束；展示有效逻辑字节／整轮时间和条目吞吐，不排除尾部等待或正常通知成本。
内存比较同范围进程的持续 RSS、峰值 RSS 和运行曲线；单进程／双进程按实际部署一致统计，双进程同时报告各端与总量。增加数据量与长历史后，不出现按总 entry 数增长的常驻明细或持续内存爬升。
依赖开销同时报告受控同负载下的 ClickHouse CPU／内存、写入与读取字节，以及真实存储 RPC 数。不能把应用内存转移为数据库或其他进程的明显额外开销后宣称总体持平。
代表场景覆盖小文件密集、大文件、大平铺目录、深层目录、长版本历史，以及较大 ACL／xattr／tags；分别记录正常路径和受影响故障恢复场景，故障场景排除人为暂停但计入实际恢复、重放和对账成本。
结论口径重复同环境 A/B，报告中位数、波动和相对差值；只有整轮性能与内存均处于正常测量波动内、没有稳定可复现的退化，才认定与优化前相当。不擅自将“相当”放宽为固定允许退化比例。

使用有界批量 ClickHouse 写入和限时刷新，复制／清理路径只负责提交事实，不等待单项持久化确认。正常终态收束异步写入；持续数据库故障按预算退出并报告缺失，不为小概率记账失败增加同步屏障或额外回执。复用元数据观察并流式计算摘要，减少重复序列化和无用途 IO。

队列、批次、在途观察和缓存同时考虑条目数与字节预算，原值与摘要持久化后按需投影、压缩和流式读取，避免巨大 ACL／xattr 常驻或重复存储。增量比较同次查询返回所需原值，不用额外查库或回源换取表面存储节省；全部成本和收益以完整正确性及实测为准。

本方案不包含全量断点续扫验收。独立扫描场景已有的 unordered／blocks、checkpoint 及专项性能规范仅在其对应范围适用，不能替代本次完整全量迁移及失败后增量的前后对比。“全量扫描损失不超过 5%”“增量扫描损失不超过 10%”及约 200 MiB 的通用内存优化目标，不作为整轮全量迁移“性能和内存相当”的替代判据。

本次验证范围：本方案仍含待实现项目，不能据文档认定全量优化已经完成。通知链路的真实 ClickHouse 单机／集群和 HTTP 故障用例见 实验室验证说明及对应测试；其证据不代表完整迁移的全部存储故障矩阵或性能／RSS 目标已通过。每次提交以实际执行结果报告已验证范围。
