# Architecture — 数据流与设计决策

## 完整数据流

```
CLI args
  └→ cli::cli_match()
       └→ app::scan / app::sync / app::ace / app::integrity_check
            └→ app::dir_walker
                 └→ data_mover::StorageEnum  (枚举 dispatch: Local / NFS / S3 / CIFS)
                      └→ NASEntry / S3Entry  (各协议 entry 类型)
            └→ transport::InProcess / QUIC
                 └→ app::receiver (双进程模式下的接收方)
            └→ sync-delta  (增量同步时的 chunk 级匹配)
            └→ app::consumer::ConsumerManager
                 ├→ DatabaseConsumer  → db::Database (ClickHouse / DuckDB)
                 ├→ StatisticConsumer (内存统计，进度广播)
                 └→ KafkaConsumer     → kafka crate (分布式模式)
```

## 统一扫描入口与检查点状态机

CLI 和 GUI 调用同一 `scan(ScanRequest)`。启用 ClickHouse 时始终使用持久化扫描：首次全量、完成后增量、中断后按检查点继续。`--resume` 仅用于要求已启用 ClickHouse，不再切换实现。不落库扫描始终全量统计，不根据作业目录推断基线。数据库错误直接上报。

共享取消模块中，流式输入及输出背压可立即取消；已发出的数据库操作则持续终止执行域内查询，并确认其结束后再退出。复制／同步的目录比对保留在独立的 `sync_catalog` 模块，不承载扫描状态机。

`[database.clickhouse] mode = "single" | "cluster"` 是唯一部署选择；集群模式还必须提供 `cluster` 名称，单机模式不接受非空集群名。默认批量 100,000。Web 设置使用同一配置类型并在保存前校验；旧 SQLite 配置在启动迁移时一次性记录模式，现有 TOML 集群配置须显式补上 `mode = "cluster"`。

扫描与复制／同步均支持两种部署。数据库层负责集群复制存储表及 Distributed 表、quorum 读写、DDL 和快照发布；业务层保持同一数据库接口。集群复制／同步目录按作业建立成对表，同一作业路由到同一 shard；扫描继续使用共享表按 job_id 隔离。集群快照发布交换物理表并使用独立 Keeper 路径，避免后续轮次复用已发布副本路径。

```
已有未完成轮次（RUNNING / FINALIZING）
  → 校验源身份、扫描选项与持久化结果
  → 按原轮次的全量/增量类型及检查点继续扫描或最终化

没有未完成轮次
  → 没有已提交基线：开始全量轮次
  → 已有已提交基线：开始增量轮次

观察与变更事件确认 → 最终化 → 统计校准 → 提交代次 → COMPLETED
取消或失败 → 保留已确认检查点，轮次不提交
重置 → 清除任务的扫描记录与基线，下次重新全量
```

- 扫描当前快照按 `(relative_path, version_id)` 唯一，`identity_key` 用于身份匹配，不能作为排序键的一部分；否则重连或对象内容变化会留下同路径旧行。旧的单机身份排序表会拒绝继续扫描，清除该任务扫描记录后重新全量扫描。
- 带稳定身份的路径缺失先做同路径复核，再持久化为候选；整轮完成后统一匹配身份与硬链接，不在每个批次扫描全量身份集合。最终聚合通过候选日志子查询读取历史决策，必要时最多读取一次整轮身份计数，保证断点恢复与跨批次重命名判定一致。
- ClickHouse 的动态批次键集合保持 WHERE 以保留索引剪枝；稀疏字面量及最终候选宽行可使用主键 PREWHERE，墓碑、工作代次和身份判断保持在 FINAL 后。旧条目先取窄主键集合，再读取宽元数据。一致性读取分摊到各副本，保留 quorum 检验和未追平重试。
- 单机扫描表使用作业后缀，包括 `base_<job_id>`、`scan_resume_<job_id>`、`incremental_<job_id>`；集群扫描使用共享表，按 job_id 隔离。

## 复制轮次的完成与恢复

复制／同步与扫描共用部署配置，但复制事务语义由 `copy_execution` 与数据库内部 `copy_generation` 管理。单作业先持有进程内数据库作业身份锁和 job_dir 文件锁，再建立轮次；同一数据库作业不能跨主机同时执行。

数据库保存复制已开始的证据、未完成标记及恢复计划摘要。摘要绑定源／目标身份、是否保留源、目标历史能力、过滤和打包等语义；凭据、并发与 QoS 不进入摘要，文件清单绑定内容摘要。Phase A 全部源枚举、比对、复制和持久化均成功后才允许删除；Phase B 同样排空并保留类型化错误。只有全部必需操作及数据库确认完成才提交轮次。

未完成轮次对相同计划、保留源、可覆盖目标执行保守重拷及路径对账，正常轮次继续使用增量比较与 rename 优化。恢复重放仍走完整对象历史分组；同一路径已有本轮确认时，旧版本只清理数据库记录，不物理删除目标。移动、版本化目标和文件清单的未完成轮次拒绝自动重放，避免删除已搬运数据、重复创建版本或把清单误当完整目录。移动任务不会使用源缺失驱动的增量删除。源文件只在对应目标的 rename 和必需内容补写成功后删除。

## 高性能 IO / Async 规则（硬性约束）

> 违反以下规则会引发 clippy warn/deny，或在 code review 中被打回。

| 场景 | 正确做法 | 禁止做法 |
|------|---------|---------|
| 大文件传输 | `Bytes` / `BytesMut` | `Vec<u8>` clone |
| 共享计数 | `AtomicUsize` | `Mutex<u64>` |
| 并发 map | `DashMap` | `RwLock<HashMap>` |
| 热点缓存 | `moka::sync::Cache` | `Arc<Mutex<HashMap>>` |
| CPU 密集 | `spawn_blocking` / `rayon::spawn` | async fn 内直接计算 |
| DB 写入 | `batch_insert` | 循环逐条 insert |
| 限速 | `QosManager` (TokenBucket) | `tokio::time::sleep` 粗粒度 |
| channel 背压 | `bounded()` 自然限流 | unbounded channel |
| 存储层 | `StorageEnum` 枚举 dispatch | `Box<dyn Storage>` |
| 热路径字符串 | `write!(&mut buf, ...)` + `buf.clear()` | `format!` / `to_string()` |
| 集合初始化 | `Vec::with_capacity(n)` | 空 Vec + 循环 push |
| 字符串 Key Map | `SmolStr` + `FxHashMap` | `HashMap<String, V>` 热路径 |
| 迭代器 | 保持惰性链 | 不必要的中间 `.collect()` |

## 设计决策

**为什么用 StorageEnum 而非 Box\<dyn Storage\>**  
枚举 dispatch 零虚表开销，编译期可知所有变体，便于穷举匹配和特化优化。热路径（dir_walker 每次迭代都调用）收益显著。

**为什么 transport 有 InProcess 和 QUIC 两种**  
单机场景用 InProcess（零拷贝 channel），跨机场景用 QUIC（低延迟 UDP 传输）。两者实现同一个消息协议（`SenderMsg` / `ReceiverMsg`），上层透明。

**为什么按持久化轮次区分全量、增量和续扫**
扫描从 ClickHouse 保存的轮次、阶段和检查点判断执行类型；作业目录只负责锁定执行与保存本地输出。目录是否存在不能证明已有完整基线。集群表按 job_id 隔离作业。

## 扫描故障与取消

识别到网络故障后，默认最多恢复 3 秒；单次存储请求的超时负责识别静默丢包，识别耗时不计入恢复窗口。恢复必须确认原失败操作能够成功。

存储故障耗尽恢复窗口后，扫描通过独立的内部取消域终止本次执行带 `log_comment` 标记的 ClickHouse 查询，并保留原始存储错误类型。用户取消令牌由用户动作控制。已发出的业务请求确认结束后，立即结束 KILL 管理轮询，避免管理请求额外延长退出时间。

界面进度与执行摘要的文件数包括符号链接，与全量扫描保持相同口径；增量内部报告仍分别保存普通文件和符号链接，Web 投影时合计，避免扫描总数漏计。

预读容量按实际写入并行度计算：全量一个窗口，增量三个窗口，每个窗口为批量大小乘实际 writer 数。全量及单机增量串行写入按一个 writer 分配，集群增量按四个 writer 分配；默认批量 100,000 条，对应全量 100,000、单机增量 300,000、集群增量 1,200,000 条预读上限。该上限约束排队条目数，不预先分配全部容量。检查点仍等待所有消费者确认后推进。源观察全部确认后，当前快照的只读统计可与旧代次最终事件处理并发；两者均结束且公共事件全部确认后，才读取本轮事件统计并提交完成状态。最终化清理中断时，已发布的重命名来源独立于候选日志重放，避免候选被部分清理后误报删除。

内存优化优先缩小排队观察记录：data-mover 共享不可变 backend 标识、按需分配冷元数据，并保留时间戳完整范围、精度和序列化语义，将当前平台的 `ObservedEntry` 从 576 字节降为 344 字节。代表性增量阶段的 Rust 活跃堆中，观察记录占约 86%；这个比例不代表整个进程 RSS 或 ClickHouse 服务端内存。

最终采用一套性能验收指标：相对同环境不落库扫描，全量及全量续扫允许 5% 差异，增量及增量续扫允许 10%，增量同时覆盖无变更和约 1% 变更。续扫同时验收恢复净吞吐和中断前后全部运行耗时，包含自动重启、重放、整理与清理，仅扣除人为暂停。2026-11-04 同一正式 release 二进制在 5,000 万文件 NFS、六副本 ClickHouse 集群上复验：不落库基线 966.88 秒；全量及全量续扫耗时分别增加 0.73%、0.99%，峰值 RSS 分别为 159.79、173.81 MiB；无变更和约 1% 变更的增量分别增加 2.63%、2.99%，峰值为 521.20、621.57 MiB；对应增量续扫分别增加 3.29%、4.36%，峰值为 554.42、752.86 MiB。三种续扫的恢复净吞吐也全部达标，三次 CLI 取消耗时为 0.127、0.159、0.214 秒。首尾不落库基线速度差约 0.0021%。优先保证性能，增量 200 MiB 目标尚未达成；这些数值是扫描进程 RSS 实测，不是内存硬上限。最高短峰发生在最终化阶段，该路径会集中保留旧项、候选项、重命名判定集合及写入批次；单次采样达到约 753 MiB 后回落，不能只用遍历阶段约 641 MiB 作为整轮峰值，也不能用 RSS 精确分摊存活对象与分配器保留页。采样曲线检查未见持续无界增长，仍须随数据规模和元数据分布重新测量。

仅已持久化候选日志对应的原生基线主键计算并保存完整公开元数据的 BLAKE3 摘要（不包含扫描代次）；普通、全量及无候选的写入保持空摘要，避免逐条摘要开销。最终化可复用候选日志的元数据，但须在 `FINAL` 后读取当前主键、代次与可空摘要，逐项确认完整且唯一的候选键集合；摘要缺失、重复或不匹配时整体读取当前宽行。空摘要不能在 `FINAL` 前过滤，普通写入默认置空以安全失效。缓存命中后使用当前基线的代次，查询错误正常上报。性能验收包含应用主动触发的整理、清理和摘要计算耗时。

backend 使用统一连接策略，不按扫描身份切换网络重试。client 负责短而有界的连接恢复和准确错误分类，backend 按操作语义处理分页、句柄与写入结果确认；普通操作的重试逐项决定，扫描的 3 秒恢复窗口只由 data-mover traversal 管理。

通用遍历入口只在调用方显式选择恢复窗口时启用协调恢复；默认普通枚举不自动重连。扫描从产品配置明确传入 3 秒，拷贝、同步、浏览与目标端枚举分别选择自己的策略。单次操作超时独立生效，即使未启用自动恢复也不会忽略时限。
