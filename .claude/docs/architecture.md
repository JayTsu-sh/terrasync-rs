# Architecture — 数据流与设计决策

## 完整数据流

```
CLI args
  └→ cli::cli_match()
       └→ app::scan / app::sync / app::ace / app::integrity_check
            └→ app::dir_walker
                 └→ data_mover::StorageEnum  (枚举 dispatch: Local / NFS / S3 / CIFS)
                      └→ NASEntry / S3Entry  (各协议 entry 类型)
            └→ transport::InProcess / QUIC
                 └→ app::receiver (双进程模式下的接收方)
            └→ sync-delta  (增量同步时的 chunk 级匹配)
            └→ app::consumer::ConsumerManager
                 ├→ DatabaseConsumer  → db::Database (ClickHouse / DuckDB)
                 ├→ StatisticConsumer (内存统计，进度广播)
                 └→ KafkaConsumer     → kafka crate (分布式模式)
```

## 统一扫描入口与检查点状态机

CLI 和 GUI 调用同一 `scan(ScanRequest)`。启用 ClickHouse 时首次全量、完成后增量；首次传入 `--resume`（GUI `scan_resume`）选择 Blocks 并保存完整目录块检查点，中断后再次带该选项恢复。不选择续扫则使用 Unordered，中断后重新开始本轮。不落库扫描始终全量统计，不根据作业目录推断基线；性能实验构建可分别测量 Blocks 与 Unordered 不落库基准。数据库错误直接上报。

共享取消模块中，流式输入及输出背压可立即取消；已发出的数据库操作则持续终止执行域内查询，并确认其结束后再退出。复制／同步的目录比对保留在独立的 `sync_catalog` 模块，不承载扫描状态机。

`[database.clickhouse] mode = "single" | "cluster"` 是唯一部署选择；集群模式还必须提供 `cluster` 名称，单机模式不接受非空集群名。默认批量 100,000。Web 设置使用同一配置类型并在保存前校验；旧 SQLite 配置在启动迁移时一次性记录模式，现有 TOML 集群配置须显式补上 `mode = "cluster"`。

扫描与复制／同步均支持两种部署。数据库层负责集群复制存储表及 Distributed 表、quorum 读写、DDL 和快照发布；业务层保持同一数据库接口。集群复制／同步目录按作业建立成对表，同一作业路由到同一 shard；扫描继续使用共享表按 job_id 隔离。集群快照发布交换物理表并使用独立 Keeper 路径，避免后续轮次复用已发布副本路径。

```
已有未完成轮次（RUNNING / FINALIZING）
  → 校验源身份、扫描选项与持久化结果
  → 按原轮次的全量/增量类型及检查点继续扫描或最终化

没有未完成轮次
  → 没有已提交基线：开始全量轮次
  → 已有已提交基线：开始增量轮次

观察与变更事件确认 → 最终化 → 统计校准 → 提交代次 → COMPLETED
取消或失败 → 保留已确认检查点，轮次不提交
重置 → 清除任务的扫描记录与基线，下次重新全量
```

- 扫描当前快照按 `(relative_path, version_id)` 唯一，`identity_key` 用于身份匹配，不能作为排序键的一部分；否则重连或对象内容变化会留下同路径旧行。旧的单机身份排序表会拒绝继续扫描，清除该任务扫描记录后重新全量扫描。
- 带稳定身份的路径缺失先做同路径复核，再持久化为候选；整轮完成后统一匹配身份与硬链接，不在每个批次扫描全量身份集合。最终聚合通过候选日志子查询读取历史决策，必要时最多读取一次整轮身份计数，保证断点恢复与跨批次重命名判定一致。
- ClickHouse 的动态批次键集合保持 WHERE 以保留索引剪枝；稀疏字面量及最终候选宽行可使用主键 PREWHERE，墓碑、工作代次和身份判断保持在 FINAL 后。旧条目先取窄主键集合，再读取宽元数据。一致性读取分摊到各副本，保留 quorum 检验和未追平重试。
- 单机扫描表使用作业后缀，包括 `base_<job_id>`、`scan_resume_<job_id>`、`incremental_<job_id>`；集群扫描使用共享表，按 job_id 隔离。
- 集群 schema 由数据库模块在每次执行内初始化一次，主存储和批次 writer 共享成功结果；失败或取消不缓存，后续调用可重试。集群 DDL 必须确认所有目标节点完成后才标记就绪。

### 扫描计数、重放与回调

扫描统一消费原生观察及 `DirectoryStatistics`，不落库扫描也使用该输入。data-mover 只返回每次目录列举的直属孩子绝对统计，不决定产品计数的持久化。`scan::statistics` 定义公共快照：scanned、filtered、retained、failed、vanished 按目录、普通文件、软链接、四类特殊文件和 unknown 分类；S3 key 只计一次，历史版本及删除标记另计。排除且不下钻的剪枝目录及子树不进入这些 entry 数，也不为统计补扫。能力声明随报告返回，unsupported/not_applicable 与实际零值分开。大小未知单独计数，逻辑文件字节不混入目录和链接元数据大小。

`EntryStatistics` 的各实现显式提供普通文件判断：原生 `ObservedView` 使用 typed kind，数据库记录读取持久化标记。公共统计的 `other_entry_count` 保存其余类型，完整扫描和增量变化总数均包含它们；特殊文件的细分类别由扫描快照提供。数据库事件汇总保留全部条目，并明确返回普通文件标记，最终化事件和恢复后的统计校准使用同一分类规则。数据模型与接口按 [agent.md](../../agent.md) 中的首次开发阶段约定维护。

扫描是否可续扫由首次运行的 `--resume` 或 GUI `scan_resume` 明确选择；不由启用数据库自动推断。可续扫使用 Blocks，普通扫描使用 Unordered。Blocks 的 periodic/final checkpoint 都只出现在完整目录块边界；平铺大目录即使超过60秒也不推进检查点。已经交付但未被 checkpoint 确认的完整块与部分块同属未确认尾部，恢复时一并回退，不按已看到的 Complete 事件自行推进。data-mover 在旧 attempt 结束后有序发出 `Resumed`，携带实际选择的 opaque checkpoint；TerraSync 校验其与已确认统计一致，只回退扫描计数及可重放事件计数，异常累计、当前恢复状态、诊断发件箱及 ACK 不回退。Unordered 的闪断恢复从根重新扫描，先清本 attempt 的扫描贡献。

`scan::progress` 只保存完成前缀和活跃目录的实际贡献：Blocks 至多一个活跃目录，Unordered 受 SDK 的并发窗口约束。没有逐条或逐目录历史账本，也不使用 SQLite、本地文件或其它本地磁盘暂存。完整统计及游标由 ClickHouse manifest 持久化。目录剪枝不补扫，不计入 scanned/filtered/retained。

数据库层 `scan_store::cuts` 管理不可变的 base/events 成对快照。开轮前先保留原基线；writer 屏障确认后封存新 cut，最后保存引用该 cut 的统计与源游标。恢复先排空旧执行的服务端查询、DDL/mutation，再读取 manifest、同步两份快照并重建 working。单机使用作业表；集群仅处理当前 job 的分区，快照使用独立 Keeper 路径，Distributed 前端仍按 job 路由。两表恢复期间禁止公开元数据访问，任一步崩溃均从同一 cut 重试；空快照可清除尾部，缺失快照明确拒绝恢复。最终化先持久化 sealed cut，再提交 generation；重启先判定提交结果，不撤回已经发布的结果。只有新 manifest 确认后才清理未引用快照。

全量扫描的最终统计只读，复用源末 FINALIZING 已确认的 cut，仅更新统计 manifest；恢复 FINALIZING 也不重新枚举源。增量最终化会写事件、删除旧事实，须封存最终化后的新 cut。是否需要新快照取决于事实是否变化，不因统计报告更新而重复克隆相同元数据。

扫描和复制共用 `job_execution` 的进程内作业注册和 job_dir 文件锁；普通数据库工厂拒绝读取活动扫描的 working 元数据。跨 Pod 同一数据库作业仍要求由任务协调器保证只运行一个执行；文件锁不是分布式租约。

最终性能验收按是否启用续扫匹配同源、同选项的基线：未启用续扫对 Unordered 不落库，启用续扫对 Blocks 不落库。两组内全量净吞吐损失不超过5%，增量不超过10%；不混用遍历顺序基线。整理、快照、最终化及清理的应用耗时均计入净运行耗时；续扫总耗时另列回退量和重扫成本，不对任意中断位置承诺固定比例的总耗时损失。

生产和性能验收的 checkpoint 间隔至少60秒；间隔到期后仍须等完整目录或子目录块结束。功能及故障测试可通过 lab-only hook 缩短间隔，其耗时与吞吐结果不进入性能验收。性能报告记录实际间隔、遍历顺序和是否中断，避免混用测试口径。

`StatisticConsumer` 的扫描终端和 HTTP 报告共用逻辑快照。旧分布按交付流/历史版本产生；无法证明是逻辑 entry 分布时不输出该分布，无法去重的目录/链接元数据大小也不输出。扫描完成和 generation 提交是两个独立状态。

异常累计数字、当前恢复状态和明细发件箱分开。发件箱最多512条，每批最多64条，每个文本字段最多2048字节；溢出有明确省略计数。失败重试保留同一批次，成功 ACK 仅移除该批前缀，不能清空后来入队的异常或数字累计。当前状态只随扫描状态变化，不随 HTTP 成功清除。完整发件箱随扫描 checkpoint 保存在 ClickHouse。Pod 丢失后的保证范围为最后已确认 checkpoint，未确认尾部与扫描条目一样可能重放；跨已完成轮次的旧明细不自动并入新轮次。

Web 接收端先验证 execution 归属，再在同一 SQLite 事务内去重事件/批次、更新有序快照和最终执行统计，提交后返回批次 ACK；同任务旧执行的明细可确认，但不得覆盖新执行进度。历史明细通过分页接口读取。Web 自身现有 SQLite 仍按其部署要求持久化；扫描不引入本地缓存，该约定不替代 Web 数据库的持久化要求。扫描正常终止回调共用2秒预算，取消和防抖失败终止共用500毫秒预算，不能为排空明细拖延退出。

## 复制轮次的完成与恢复

复制／同步与扫描共用部署配置，但复制事务语义由 `copy_execution` 与数据库内部 `copy_generation` 管理。单作业先持有进程内数据库作业身份锁和 job_dir 文件锁，再建立轮次；同一数据库作业不能跨主机同时执行。

数据库保存复制已开始的证据、未完成标记及恢复计划摘要。摘要绑定源／目标身份、是否保留源、目标历史能力、过滤和打包等语义；凭据、并发与 QoS 不进入摘要，文件清单绑定内容摘要。Phase A 全部源枚举、比对、复制和持久化均成功后才允许删除；Phase B 同样排空并保留类型化错误。目录元数据在 payload、删除和消费者写入全部结束后，由 `copy_completion` 统一查询及回写；目录查询、更新和任务失败保留原始类型，并等待已启动任务收尾。查询与进度线程由执行域持有，更新任务连同完成结果最多保留 32 个，避免按目录总数积累任务。目录元数据全部确认后才提交数据库轮次并发布最终生命周期结果，失败时保留未完成标记供安全重试。

未完成轮次对相同计划、保留源、可覆盖目标执行保守重拷及路径对账，正常轮次继续使用增量比较与 rename 优化。恢复重放仍走完整对象历史分组；同一路径已有本轮确认时，旧版本只清理数据库记录，不物理删除目标。移动、版本化目标和文件清单的未完成轮次拒绝自动重放，避免删除已搬运数据、重复创建版本或把清单误当完整目录。移动任务不会使用源缺失驱动的增量删除。源文件只在对应目标的 rename 和必需内容补写成功后删除。

## 高性能 IO / Async 规则（硬性约束）

> 违反以下规则会引发 clippy warn/deny，或在 code review 中被打回。

| 场景 | 正确做法 | 禁止做法 |
|------|---------|---------|
| 大文件传输 | `Bytes` / `BytesMut` | `Vec<u8>` clone |
| 共享计数 | `AtomicUsize` | `Mutex<u64>` |
| 并发 map | `DashMap` | `RwLock<HashMap>` |
| 热点缓存 | `moka::sync::Cache` | `Arc<Mutex<HashMap>>` |
| CPU 密集 | `spawn_blocking` / `rayon::spawn` | async fn 内直接计算 |
| DB 写入 | `batch_insert` | 循环逐条 insert |
| 限速 | `QosManager` (TokenBucket) | `tokio::time::sleep` 粗粒度 |
| channel 背压 | `bounded()` 自然限流 | unbounded channel |
| 存储层 | `StorageEnum` 枚举 dispatch | `Box<dyn Storage>` |
| 热路径字符串 | `write!(&mut buf, ...)` + `buf.clear()` | `format!` / `to_string()` |
| 集合初始化 | `Vec::with_capacity(n)` | 空 Vec + 循环 push |
| 字符串 Key Map | `SmolStr` + `FxHashMap` | `HashMap<String, V>` 热路径 |
| 迭代器 | 保持惰性链 | 不必要的中间 `.collect()` |

## 设计决策

**为什么用 StorageEnum 而非 Box\<dyn Storage\>**  
枚举 dispatch 零虚表开销，编译期可知所有变体，便于穷举匹配和特化优化。热路径（dir_walker 每次迭代都调用）收益显著。

**为什么 transport 有 InProcess 和 QUIC 两种**  
单机场景用 InProcess（零拷贝 channel），跨机场景用 QUIC（低延迟 UDP 传输）。两者实现同一个消息协议（`SenderMsg` / `ReceiverMsg`），上层透明。

**为什么按持久化轮次区分全量、增量和续扫**
扫描从 ClickHouse 保存的轮次、阶段和检查点判断执行类型；作业目录只负责锁定执行与保存本地输出。目录是否存在不能证明已有完整基线。集群表按 job_id 隔离作业。

## 扫描故障与取消

识别到网络故障后，默认最多恢复 3 秒；单次存储请求的超时负责识别静默丢包，识别耗时不计入恢复窗口。恢复必须确认原失败操作能够成功。

存储故障耗尽恢复窗口后，扫描通过独立的内部取消域终止本次执行带 `log_comment` 标记的 ClickHouse 查询，并保留原始存储错误类型。用户取消令牌由用户动作控制。已发出的业务请求确认结束后，立即结束 KILL 管理轮询，避免管理请求额外延长退出时间。

界面进度与执行摘要的文件数包括符号链接，与全量扫描保持相同口径；增量内部报告仍分别保存普通文件和符号链接，Web 投影时合计，避免扫描总数漏计。

预读容量按实际写入并行度计算：Unordered 全量一个窗口，Blocks 全量及两种增量三个窗口，每个窗口为批量大小乘实际 writer 数。全量及单机增量串行写入按一个 writer 分配，集群增量按四个 writer 分配；默认批量 100,000 条，对应 Unordered 全量 100,000、Blocks 全量 300,000、单机增量 300,000、集群增量 1,200,000 条预读上限。该上限约束排队条目数，不预先分配全部容量。检查点仍等待所有消费者确认后推进。 writer 排空后，数据库模块并行复制 base/events 两张独立事实表，等待两者全部结束并成功才返回快照 token；任一复制失败不发布半个快照，取消仍负责结束所有在途请求。源观察全部确认后，当前快照的只读统计可与旧代次最终事件处理并发；两者均结束且公共事件全部确认后，才读取本轮事件统计并提交完成状态。最终化清理中断时，已发布的重命名来源独立于候选日志重放，避免候选被部分清理后误报删除。

内存优化优先缩小排队观察记录：data-mover 共享不可变 backend 标识、按需分配冷元数据，并保留时间戳完整范围、精度和序列化语义，将当前平台的 `ObservedEntry` 从 576 字节降为 344 字节。代表性增量阶段的 Rust 活跃堆中，观察记录占约 86%；这个比例不代表整个进程 RSS 或 ClickHouse 服务端内存。

数据库公共查询列由一个投影入口生成，只有生成原生扫描事实行（base 及 staging）时才编码 snapshot；事件行直接生成公共投影。集群事件序列化借用记录，记录持有期覆盖完整重试，非空事件仍在顺序 quorum 确认后才允许写 base。空事件检查取消后直接返回，不等待其它批次的事件锁。普通批次仅清理自己持有的 staging 分区；删除使用的 keys 分区由独立编号和删除操作管理，执行结束仍清理遗留分区。

性能验收按遍历方式分别建立不落库基线：未传 `--resume` 的全量和增量使用 Unordered；传入 `--resume` 的首次扫描与续扫使用 Blocks。全量及全量续扫的净吞吐损失不得超过 5%，增量及增量续扫不得超过 10%，增量同时覆盖无变更和真实约 1% 文件增删改。性能测试的 checkpoint 间隔至少为 60 秒，到期后等待完整目录或子目录块结束；平铺大目录未完成时不得中途保存。功能及故障测试可以缩短间隔，其耗时不得用于性能验收。续扫按已确认前缀之后的唯一条目计算恢复净吞吐，另外报告取消、回退、重扫、重新启动、整理与清理的总运行耗时，扣除人为暂停等待。单机与真实集群均须验证，并记录扫描进程峰值 RSS、采样曲线和最终化阶段的内存；约 200 MiB 是优化目标，优先保证性能，不作为硬上限。切换目录块 checkpoint 之前的历史结果不能作为当前路径的性能通过依据。

仅已持久化候选日志对应的原生基线主键计算并保存完整公开元数据的 BLAKE3 摘要（不包含扫描代次）；普通、全量及无候选的写入保持空摘要，避免逐条摘要开销。最终化可复用候选日志的元数据，但须在 `FINAL` 后读取当前主键、代次与可空摘要，逐项确认完整且唯一的候选键集合；摘要缺失、重复或不匹配时整体读取当前宽行。空摘要不能在 `FINAL` 前过滤，普通写入默认置空以安全失效。缓存命中后使用当前基线的代次，查询错误正常上报。性能验收包含应用主动触发的整理、清理和摘要计算耗时。

backend 使用统一连接策略，不按扫描身份切换网络重试。client 负责短而有界的连接恢复和准确错误分类，backend 按操作语义处理分页、句柄与写入结果确认；普通操作的重试逐项决定，扫描的 3 秒恢复窗口只由 data-mover traversal 管理。

通用遍历入口只在调用方显式选择恢复窗口时启用协调恢复；默认普通枚举不自动重连。扫描从产品配置明确传入 3 秒，拷贝、同步、浏览与目标端枚举分别选择自己的策略。单次操作超时独立生效，即使未启用自动恢复也不会忽略时限。
